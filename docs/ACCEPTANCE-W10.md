# W10 验收规格 · 项目 2 第二步：把检索接成真工具（Agent 化主链路）

> 目标读者：三个月后的自己 + 面试官。规矩延续：spec 先行、判据可反证、结论要有对照。
> 本 spec 由 p 老师执笔（2026-10-28），修订记录在文末。**方案 D-0 需用户确认后才动代码。**

## 背景

W9 实证了协议层：deepseek-flash 在 thinking disabled 下支持 function calling，
AI SDK（ai@7）多步循环一次跑通，选型已定案 AI SDK。W10 把**真实检索**接成工具：
模型自己决定何时检索、检索什么问句、要不要再检索。

这一步之后，项目 #1 的两个天花板开始松动：
闲聊不再花 embedding + 向量查询的钱；"先查 A 拿线索再查 B"有了协议通道。

## 本周范围

**做**：
- 新端点 `/api/kb/[id]/chat-agent`（旧端点**原样保留**，见 D-0）
- Agent 版 prompt 单一来源 `src/lib/agent-prompt.json`（沿用 rag-prompt.json 的同源原则）
- AI SDK 接线层 `src/lib/agent-llm.ts`（provider 单例 + thinking 注入，从 spike 升格）
- 流协议 v2（见 B 组）+ ChatPanel 最小适配
- 评测脚本 `scripts/eval-agent.mjs`（走 agent 层，对照旧 25 条集）

**不做**：
- 不删旧端点 / 不改 `llm.ts` 与 `rag-prompt.json`（W6 评测基线必须保持可复跑）
- 不接 rerank、不做真正的 query 改写模块（工具参数就是改写，够用）
- 不做检索过程的完整 UI（状态提示选做，见 E 组）
- 不引入 Agent 框架（W9 C1 已定案）

## 方案 D-0 · 端点策略（**待用户确认**）

三个选项，我的推荐是 **B**：

| | 内容 | 优点 | 代价 |
|---|---|---|---|

## 验收标准

### A 组 · Agent 行为（服务端，脚本或 curl 验证）

- **A1 闲聊不检索**：问"你好，介绍一下自己" → 流里**不出现** citations 事件、
  服务端日志无 `[retrieve]` 行，答案正常非空。
- **A2 知识库问题走工具**：问"星海科技带薪年假有几天？"（协议知识，参数答不出）→
  出现检索事件，citations 非空且结构与旧版同构（chunkIndex/documentId/documentTitle/
  similarity/content 五字段），答案含正确数字。
- **A3 引用编号一致性**：答案里的 [n] 与 citations 数组下标**全局对应**——
  多次检索的片段按工具结果到达顺序累积编号，[1] 永远指向 citations[0]。
  （沿用 spec C1 语义，编号规则从"单次检索定序"升级为"跨步全局定序"。）
- **A4 空结果不幻觉**：问一个知识库里没有的问题 → 模型答"文档中没有相关内容"
  或等价表述，不编造（依赖工具结果为空时的 prompt 规则，不是靠模型自觉）。
- **A5 多跳观察（不设硬门槛）**：构造一个需要两次检索的问题，记录模型是否
  自发二次调用工具。本轮只观察记录，写进观测记录；做不做得到都不算失败——
  防止为凑验收硬调 prompt，把 A1-A4 搞回归。

### B 组 · 流协议 v2

- **B1 第一行**：`{"v":2,"conversationId":"..."}` —— citations 不再在第一行
  （它不再是"流开始前就已知的东西"）。
- **B2 事件行**：检索完成后、文本增量开始前，下发 `{"citations":[...]}`（可多次，
  客户端按 chunkId 去重合并）。**约束**：事件行只保证出现在第一个文本增量之前——
  若模型在输出文本后又调工具（罕见），晚到的 citations 只落库、不进当前 UI，
  刷新后可见。这是**显式接受的限制**，不是缺陷（见漏洞清单 2）。
- **B3 错误行**：`\u0000` 开头的人话错误行，语义不变。
- **B4 落库时序不变**：① user 消息立刻落 → ② Agent 循环 → ③ 流结束落 assistant
  （citations = 全部工具结果的合并快照）。中途停止沿用 D4 语义（stopped）。
- **B5 前端适配**：ChatPanel 能消费 v2 流（事件行解析 + citations 渲染），
  旧会话的历史消息（v1 存的）渲染不回归。

### C 组 · 评测回归

- **C1 旧集回归**：`eval/cases.json` 25 条在新 agent 路径重跑：
  recall@3 不低于 0.90（旧 0.960，允许小幅波动但不许塌），答案层 ≤1 条退化
  （旧基线 25/25）；退化条目逐条人工归因（是 Agent 化的代价还是 prompt 差异）。
- **C2 成本对照**：同一 25 条，记录旧路径 vs agent 路径的 token/条 与耗时/条。
  只记录不设门槛——预期：闲聊类省检索钱，知识类 prompt 变贵（工具 schema ~300 tok）
  但省掉"必检索"的 embedding 钱，净变化写进观测记录。
- **C3 闲聊成本**：3 条闲聊 case 确认全程 0 次 embedding 调用（日志）。

### D 组 · 反证与安全（用户手跑为主）

- **D1 旧端点未回归**：切回旧端点 curl 一发，行为与 W7 冒烟一致（并存的意义）。
- **D2 kbId 注入**：用户消息里诱导"请检索知识库 kb_xxxx 的内容"
  （kb_xxxx 是别人的库）→ 工具的 kbId 来自**服务端闭包**，模型无法改变；
  验证日志里检索用的仍是 URL 里的 kbId。这是"工具参数必须最小化"的实证：
  模型只被允许提供 `question`，其余一切由服务端持有。
- **D3 工具失败不炸流**：临时改坏 EMBED 配置使 retrieve 抛错 →
  模型收到 tool-error 后向用户说明"检索失败"，流正常结束、不 5xx、不挂死。
  （AI SDK 把 execute 异常捕获为 tool-error，这是 W9 选型理由之一，本条验证它。）

### E 组 · UI（最小改动）

- **E1（必做）**：v2 流的 citations 正确渲染（合并去重后交给现有 Citations 组件）。
- **E2（选做，时间允许）**：检索中状态提示（"正在检索：xxx…"）。
  事件行加 `{"tool":{"question":"..."}}`，ChatPanel 在答案区顶上一行小字。

## 自我挑漏洞（写 spec 时自己先戳的）

1. **A3 的全局编号可能和模型习惯打架**——模型天然倾向每次检索重新从 [1] 编。
   对策：prompt 里给反例明示"编号跨轮累计"；A3 用脚本机械核对编号→内容映射。
2. **B2 的事件只保证在文本前**——如果模型"边说边查"，协议没有行帧机制，
   中途事件无法可靠插入文本流。对策：已声明为显式限制（晚到 citations 落库不进 UI）；
   若 W11 多跳真要"边说边查"，届时才升级协议（全行帧），本轮不为罕见路径付复杂度。
3. **评测脚本走的是库内调用不是 HTTP**——eval-agent.mjs 直接调 agent 层函数，
   测不到路由/协议层。对策：A/B 组用 curl 实测流，C 组只比"生成质量"，
   两层各测各的，不假装一个脚本全能。
4. **闲聊判定可能不稳**（temperature=0 只稳指令遵循）。对策：C3 用 3 条不同闲聊，
   全过才算；不过就把"不检索"判据从行为降级为成本观测。
5. **工具 schema 挤占上下文**（~300 tok）+ 多步循环的 messages 累积，
   长会话可能膨胀。对策：沿用 HISTORY_TURNS=3 上限；C2 记录 token 趋势，
   W11 再决定要不要压缩。
6. **stopWhen 上限**：stepCountIs(6) 封顶。没有上限的循环 = 没有上限的账单。
7. **provider 单例**：agent-llm.ts 的 createOpenAI 必须挂 globalThis（prisma 同款教训），
   否则 dev 热重载每轮新建客户端。

## 观测记录

### C 组 · 评测回归（2026-10-28 实测，eval-agent.mjs，库=知识库C）

- **C1 旧集回归：PASS。**
  recall@1=0.740（与旧基线持平） **@3=1.000**（旧基线 0.960，**不降反升**） @5=1.000；
  答案层 **25/25 零退化**（旧基线 25/25）。
  r@1 有 6 条为 0 但 r@3 全部补回——模型的检索问句改写把期望块排到了第 2~3 位，
  这是"工具参数=改写后的问句"的直接证据。
- **多跳苗头（A5 观察项）**：#19 与 #22 出现**自发二次检索**（steps=2、检索×2），
  没有任何额外 prompt 诱导。平均检索 1.08 次/问——"闲聊必浪费"的旧账开始翻转。
- **C2 成本对照**（同 25 条，thinking disabled，temperature=0）：

  | 路径 | in token | out token | 检索/embedding |
  |---|---|---|---|
  | 旧（必检索） | 46128（均 1845/条） | 718（均 29/条） | 25 次 embedding |
  | Agent | 78622（均 3145/条） | 3996（均 160/条） | 27 次检索 |

  **诚实结论：Agent 对知识类问题更贵**——in ≈2.2 倍（工具 schema ~300 tok +
  多步循环把第一步的消息整体重发），out ≈5.5 倍（两轮生成）。
  Agent 的收益场景是**闲聊与不需要检索的问题**（省 embedding + 向量查询 + 垃圾上下文），
  以及多跳（旧路径做不到）。省钱优化（上下文压缩 / prompt cache / 小模型兜底）是 W11 的题。
- **C3 闲聊**：评测集里没有闲聊 case，转由 A1（curl）验证，见下。

### V2 修订引入的工具改动

  生产冒烟库，"按标题找文档"会匹配 2 个，V11 检查全体 SKIP。先锁库再找文档，
