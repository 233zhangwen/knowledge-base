## 0. 为什么这个 W 值得单独做

W15 的 rerank 解决了"从候选里挑对的块"。但 c19 暴露了下一层问题：

> 问：「一名正式员工在同一年里休完年假与婚假，合计最多可休多少天带薪假期？」
> 两块证据（年假 17 天、婚假 12 天）**都在 top5 里**，模型答不出 29。

证据齐了，答不出来 —— 这说明瓶颈已经从「检索」转移到「编排」。

面试价值的差别在这里：

| 讲法 | 面试官的反应 |
|---|---|
| "我接了 rerank，recall 涨了" | 你调了个 API |
| "我发现 rerank 治不了符号消歧，那是元数据问题" | 你有判断力 |
| **"我的 Agent 能多跳、能压上下文，并且我能证明每一步都必要"** | 你搭过系统 |

前两条 W15 已经拿到了。W16 要拿第三条，而它的难度不在写代码，在**造出真需要多跳的问题**。

## 1. 先看清这次要打的是什么

### 1.1 现在的 Agent 其实"能"多跳，只是从来不做

`agent-llm.ts` 里 `AGENT_MAX_STEPS = 6`，模型理论上可以连调 6 次检索。但实际行为是：

```
问题 → retrieve_knowledge(问句原样) → 拿到 5 块 → 直接作答
```

**一次检索就收工**。`eval-agent.mjs` 的统计里「平均检索次数」这个数一直没被当回事 —— W16 第一件事就是把它变成主指标。

为什么模型不跳：
- 工具描述说"先调用本工具检索"，没说"如果不确定就再查一次"
- 没有任何东西提示它"这个问题包含几个子问题"
- prompt 里没有"证据不足要继续查"这条规则

### 1.2 两种"跳"必须分开，因为解法完全不同

这是本周最容易搞混、也是最能体现深度的地方：

| 类型 | 定义 | c19 属于 | 解法 |
|---|---|---|---|
| **推理跳** | 证据都在手里，但要做多步推导/计算/比较 | ✅ | prompt 要求「先分解、再逐步计算、最后合并」 |
| **检索跳** | 第一次检索拿不到全部证据，必须换 query 再查 | ❌ | 规划 + query 改写 + 多次检索 |

c19 是**推理跳**。它不需要第二次检索，需要的是"别急着总结，先把 17 和 12 对着问题算一遍"。

**如果本周只做检索跳，c19 依然答不出。** 这是 spec 里必须写死的预期，避免 W16 收工时拿"多跳做完了但 c19 还是错"当失败，或者更糟——拿"平均检索次数变多了"当成功。

### 1.3 上下文膨胀是第二个问题，而且已经有现成的浪费

多跳一旦真的发生：

```
3 次检索 × 5 块 × 500 字 ≈ 7500 字 ≈ 4000 token
```

但有件事现在就在发生，不用等多跳：

```ts
// agent-llm.ts formatChunks 现状
let no = ledger.numbers.get(c.id);
if (no === undefined) { 分配新编号; push 到 citations }
return fenceChunk({ no, title, chunkIndex, content, suspicious });  // ← 原文照旧完整注入
```

**编号复用了，原文没有。** 第 2 次检索命中同一个块时，模型看到的是同一段话第二遍，只挂了个相同编号。这不产生任何信息，只产生 token 和注意力稀释。

这就是本周第一个抓手：**去重是免费的**。它不需要 LLM，不需要摘要，不会丢证据，而且能直接量化（token 省了多少）。

### 1.4 所以本周的真实形状

```
A 组（前置）造多跳题 → 证明"单跳确实答不出" → 才有资格谈收益
   ↓
B 组 规划（让模型知道要跳）
   ↓
C 组 压缩（让跳完之后上下文还干净）
   ↓
D 组 评测（多跳题涨 + 单跳题不许退 + 成本可接受）
```

A 组不做完，B/C 组做了也不知道有没有用 —— 这是 W15 刚教过的课，别第二次踩。

## 2. A 组：造多跳用例（前置，没做完不许进 B 组）

### A0 先修评测漂移（技术债，必须最先做）

`scripts/eval-agent.mjs` 里的 `searchChunks()` 是 `retrieve.ts` 的**手抄副本**，而且抄的是 W13 之前的版本：

| 能力 | 线上 `retrieve()` | `eval-agent` 的副本 |
|---|---|---|
| rerank 精排 | ✅ W15 | ❌ 没有 |
| RECALL_K 粗排 | ✅ 10 | ❌ K=5 直出 |
| 围栏 `<<<DOC>>>` | ✅ W14 | ❌ 裸拼 `[n] ＋原文` |
| suspicious 标记 | ✅ W14 | ❌ 没有 |

**结论：这个脚本评测的是一个线上不存在的系统。** W14 的注入防御、W15 的 rerank，agent 路径一次都没被测过。

修法（按优先级）：
1. **首选**：把 `eval-agent.mjs` 改成 `.mts`，直接 `import { retrieve, TOP_K } from '../src/lib/retrieve.ts'` —— 与 W15 的 `seed-kb-fixtures.mts` 同一套路（`allowImportingTsExtensions` 已开）。风险是脚本里跑 Prisma 7 + driver adapter，需先探通。
2. **退路**：探不通就抽一个 `buildRetrieveSql()` 之类的最小共享函数，两份都调它。但这是次优解——**共享 SQL 不等于共享行为**，rerank 之后的逻辑还是会漂。

验收：`eval-agent` 打印的 K 与 `RECALL_K` 都从源码读（不写死），且跑出来能观察到 rerank 生效。

### A1 三类多跳题（每类 2~3 条，共 8 条）

依赖已经存在的交叉引用（不用改任何文档，W15 的块指纹全部安全）：

| 类型 | 定义 | 素材（现成的） |
|---|---|---|
| **桥接 bridge** | A 文档给指针，答案在 B 文档 | I 第 8 行「本办法未尽事项按《员工手册》执行」+ I 第 24 行「转正后年假按《员工手册》折算」 |
| **组合 compose** | 问题横跨两份文档，各出一半 | F 第 82 行「婚丧产按母公司标准执行」+ C 的婚假条款 |
| **聚合 aggregate** | 要遍历多块求最值/求和/列举 | 「五份制度里哪些规定了 X 天的期限」 |

每条 case 新增三个字段：

```jsonc
{
  "id": "m01",
  "type": "bridge",          // bridge | compose | aggregate
  "minHops": 2,              // 最少需要几次检索
  "evidence": [              // 证据可能落在哪些块（跨文档！）
    { "documentTitle": "I-...", "index": 5 },
    { "documentTitle": "C-...", "index": 5 }
  ]
}
```

### A2 ⚠️ 硬门槛：必须验证"单跳答不出"

**每条多跳题都要先跑一次单检索，确认 top5 覆盖不到全部证据。**

不验证的后果：每条题都"看起来像多跳"，实际一次检索全拿到，模型照答对，然后 B/C 组做完发现指标一点没动，还以为是规划没写对。

验证方式（新增 `--probe` 模式）：

```
对每条 case，只用原问题检索一次（TOP_K=5）
→ 统计 evidence 里有几块被覆盖
→ 覆盖率 < 100% 才算合格的多跳题
→ 覆盖率 = 100% 的，要么改问题让它更含糊，要么弃用
```

这条纪律要写进脚本的输出里，不能只写在文档里。

### A3 现有 45 条的地位

**全部保留，作为"单跳不许退化"的对照组。**

W16 的所有改动都是在给 Agent 加东西，加东西一定会让某些题变差（多一次检索 = 多一次引入噪声的机会）。没有这 45 条兜底，"多跳涨了"这个结论是片面的。

## 3. B 组：规划

### B1 三种实现，成本差一个数量级

| 方案 | 额外 LLM 调用 | 可观测性 | 风险 |
|---|---|---|---|
| ① prompt 内规划 | 0 | 低（只能看它实际检索了几次） | 模型可能不遵守，且不可验证 |
| ② 独立规划步骤 | +1/问 | 高（计划是结构化 JSON，可断言） | 多一次延迟和一次失败点 |
| ③ 混合（分类器判断） | +0~1 | 中 | 分类器本身是新的失败点 |

**决策 1 待拍。**

### B2 无论选哪个，这两件事必须做

1. **工具描述要改**。"必须调用本工具"只是"至少调一次"，不包含"不够就再调"。要显式写清什么情况下应该再检索（答案里出现"参见""按《X》执行""另有规定"这类指针时）。
2. **prompt 改动必须同源**。`agent-prompt.json` 是线上与评测的单一来源（这份纪律已经守了两个 W），规划指令进这个文件，不许写死在 `.ts` 里。

### B3 推理跳单独一条规则（针对 c19）

不管规划怎么做，加一条：

> 问题要求"合计""最多""总共""相比"这类运算时，先把每个分项的证据与数值单独列出来，再逐步计算；不要跳过中间步骤直接给结论。

这条与规划正交，可以独立验证（c19 从 ✗ 变 ✓ 就算赢）。

## 4. C 组：上下文压缩

### C1 三档，从免费到昂贵

| 档 | 手段 | 代价 | 损失 |
|---|---|---|---|
| **C1-a** | 同一 chunkId 二次命中只回编号占位，不重复原文 | 0 调用 | 无 |
| **C1-b** | 累积块数超过上限时，按 rerankScore 保留前 N，其余从上下文移除 | 0 调用 | 有（可能移掉证据） |
| **C1-c** | LLM 把历史块压成摘要 | +1 调用/轮 | 有（摘要可能篡改数字） |

**决策 2 待拍**，我的倾向写在决策区。

### C2 C1-b 的隐藏地雷：引用悬空

如果从上下文里移掉了块，但前端 citations 里还有它、模型还能标 `[7]` —— 用户点开引用发现"这段内容答案里根本没提"。

处理原则：**移除上下文的块，编号必须一起作废**（维护 `chunkId → 编号` 的 active 集合，或者干脆重新编号）。这是 D 组要重点验的一条。

### C3 压缩必须可量化

不量化就等于没做。指标：
- 平均注入 token / 问（对比 W16 前）
- 重复注入块数（C1-a 应该把它打到 0）
- 证据丢失率（压缩后，预期块还在不在上下文里）

## 5. D 组：评测（判据先写死）

### D1 指标

| 指标 | 含义 | 关注点 |
|---|---|---|
| **多跳成功率** | 8 条多跳题答对数 | 主收益 |
| **单跳成功率** | 45 条里非多跳的 | **红线：不许退化** |
| 平均检索次数/问 | 是否真的跳了 | 诊断 |
| 平均 input token/问 | 压缩效果 | 诊断 |
| p95 延迟 | 多跳的代价 | 预算 |

### D2 判据（先定，不许事后改）

- **多跳题**：通过数 ≥ 6/8（75%）
- **单跳题**：通过数 **不低于** W16 基线（一次都不许少）
- **成本**：平均 input token 增幅 ≤ 60%；p95 延迟 ≤ 12s
- **可解释**：每一档增益都要能指到具体 case，不接受"总体涨了"

> W6 的教训：总指标涨了不代表每条都涨。W15 又验了一次（7 条倒退）。
> 这次要求更严：**任何一条从 ✓ 变 ✗ 都要有解释**，解释不了就回滚那一项改动。

## 8. 待决事项

### 决策 1：规划放哪 → **① prompt 内规划（已选）**

- **① prompt 内规划（已选）** —— 0 额外调用，先看模型自己能不能做到；做不到再升级。符合本项目"先测再改"的一贯做法，也能给方案②提供对照基线
- ② 独立规划步骤 —— 可观测、可断言，但每问固定 +1 次 LLM 调用（约 +1.5s、+800 token）
- ③ 混合（小分类器判断复杂度）—— 理论最优，但引入第三个失败点，且分类器本身需要标注数据

> 备注：若选①，D2 判据不变。①做不到 75% 就说明该升级，不是把判据调低。
> **升级路径**：若 D5 跑完多跳通过数 < 6/8，先在 `eval/multihop-results.md` 记录"prompt 内规划的能力上限"，
> 下周（或本周末）再上方案②，用同一批用例对照 —— 那时"为什么要多花一次调用"有数据支撑，不是拍脑袋。

### 决策 2：压缩做到哪一档 → **① 无损（已选）**

- **① C1-a + C1-b（已选）** —— 只做无损去重 + 超限裁剪，不引入摘要。摘要会篡改数字，而这个项目的核心卖点是"引用可溯源"，让一个可能改数字的环节横在中间是自相矛盾的
- ② 只做 C1-a —— 最保守，但多跳 3 次以上时 token 还是会上去
- ③ 全做（含 LLM 摘要）—— 压缩率最高，代价是证据可能被摘要改写，且要额外验证"摘要没改数字"

> 落地含义：`context-budget.ts` 只做**字符串与编号层面的运算**，不许出现任何 LLM 调用 ——
> 这样它就是一个纯函数模块，能被单测完整覆盖（同时也守住了 W13 那条"纯函数别和建连模块混住"的教训）。

### 决策 3（不拍板，说明我的建议）

**多跳题要不要进 `cases.json` 主集？** 建议进。理由是主集是唯一的回归防线，分开放会变成"跑主集时不测多跳"，也就是永远不测。代价是主集从 45 条变 53 条，单次评测时间上升约 18%。

### 10.3 与 spec 的四处偏差（逐条说明）

**① 多跳题从 8 条变成 3 条，判据从 ≥6/8 变成"样本不足"。**

造了 7 条，`--probe` 只放行 3 条。原因见报告 3.3：40 块的库上，人事类证据块一共五六个，问题落在同一领域内时 rerank 一次就端全了。合格的多跳题必须"问句带强主体锚点 + 第二跳证据在另一领域"，这类交叉点本来就少。

**没有为了凑数量放宽 probe 门槛** —— 那等于把自己骗过去。4 条被否决的降级成单跳回归题保留。

**② 规划从"prompt 内"变成"代码检测 + 模型执行"。**

spec 决策① 选的是 prompt 内规划。实测发现条件句式的规则模型判不准，导致 49 条单跳题平均检索从 1.13 涨到 2.63。改成正则检测（`pointerHints`）+ 工具结果末尾加一行提示后降到 2.42。

结论没变（仍然是"prompt 内、零额外 LLM 调用"），变的是**判断权归属**：判断交给代码，执行留给模型。

**③ C1-b（超限裁剪）没做，改成入口的检索预算。**

流式已经发出去的内容撤不回来，"不再注入新块"等于丢证据。改成在工具入口限制调用次数（3 次），超限返回提示而不是抛错。

**④ token 判据未通过（+107% vs ≤60%）。**

如实记录，未调判据。这一版的处理见报告第 6 节：把成本与正确性的取舍交出去，而不是替用户决定。

### 10.4 三条值得单独记下的判断

1. **评测副本比没有评测更危险。** 它给了你一个数字，那个数字看起来像证据。W15 因此把 c19 判成"能力边界"，而真代码一次就跑对了。用解析钩子替代复制副本，是从机制上消灭这类漂移，不是靠"记得同步"。

2. **判据误判的方向是固定的。** 关键词匹配只会把对的判成错的，不会反过来。于是你看到成绩不好就去改系统 —— 治的是假病。所以修判据的优先级高于调系统。

3. **能用确定性测试验证的，绝不用概率性输出验证。** 第一次想用 token 证明去重有效，结论是"反而涨了"，因为那次模型多检索了一次。换成记录重复块数（与调用次数无关的比率）才看得清：26% → 20.5%。
