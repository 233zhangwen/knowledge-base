## 一、三个决策（先定，判据才站得住）

### 决策① 评测集 = 仓库内的 JSON 文件（`eval/cases.json`）

**结论**：评测集不进数据库，以 JSON 文件进 git。

推理链：
- 评测集必须**可携带**：换机器、换数据库环境（比如 W7 部署到 Neon 生产库）都要能跑。
  进数据库意味着"评测数据和某个库实例绑死"，正好毁掉这一点。
- 10~20 组的规模，JSON 完全够；为它建表、写 CRUD 是用架构讨好不存在的问题
  （W4 拒绝 AI SDK、W5 标题不调 LLM 是同一个判断）。
- 进 git 还有作品集价值：面试官能直接看到"这个人的评测集长什么样、覆盖了什么"。

**代价（必须显式接受）**：问题文本和 C 手册的内容耦合。手册更换/重新索引后，
评测集必须重标注 —— 这条代价本身被 A3 验收。

### 决策② 检索层自动判分（recall@5）；答案层人工抽检

**结论**：
- 检索层：embedding 检索是**确定性**的（同输入给出同样的排序），自动判分可靠。
  指标用 **recall@k**：一个 case 的得分 = 命中期望片段数 ÷ 期望片段总数；
  总分 = 全部 case 得分的平均。**同时报 @1 / @3 / @5 三个数**（@5 与线上
  TOP_K 对齐，@1/@3 在小库上才有区分度 —— 见 V13 的实测）。
- 答案层：`eval.mjs --with-llm` 才调 LLM 生成答案，人工对照
  `answerMustContain` 关键词抽检。默认**不调 LLM**。

推理链：
- 为什么不是 hit@K（命中任一即 1 分）：hit@K 会把"5 个期望片段只命中 1 个"
  和"全部命中"打成同分，信息量太低，调优时看不出梯度。recall@K 保留梯度。
- 为什么答案层不自动判：关键词匹配太脆（答案换个说法就误判），
  LLM-as-judge 引入第二个模型的不确定性且已划入 Out of Scope。
  十几到二十组的量，人工看答案是最便宜且最可靠的方案 —— **人工不是妥协，
  是这个规模下的最优解**。

### 决策③ 调优回路 = 一次只改一个参数，改前后各跑一次

**结论**：基线数字 → 改**一个**参数（TOP_K / 切片目标长度 / 重叠 / 分隔符 /
embedding 模型，**五选一**）→ 重跑评测 → 数字对比 → 结论写进 `eval/RESULTS.md` →
若变差则回滚并记录原因。**一次改两个参数就无法归因，直接违规。**
prompt 类改动**不在这个回路里**（V3：recall@5 只看检索层，改 prompt 分数必然
纹丝不动，拿它验"调优有效"是自欺），它走 C4-b 的人工对照口径。

推理链：
- 评测的全部价值在于对比，对比的有效性取决于归因，归因的前提是单变量。
- 回滚记录（C3）是这套体系防"表演化"的关键：没有失败案例的调优记录，
  等于"一直改到数字好看为止"，那不是评测，是装修。

## 二、A 组：评测集本身

**A1 评测集形态固定、能被脚本校验**
- 判绿：`eval/cases.json` 存在，顶层是数组，每条 case 结构为
  ```json
  {
    "id": "c01",
    "documentTitle": "C-星海科技员工手册-完整版(B1专用)",
    "question": "年度额度最高的是哪一项？",
    "expectChunks": [{ "index": 4, "snippet": "培训基金" }],
    "answerMustContain": ["8000", "培训"]
  }
  ```
  字段含义：`documentTitle` 用于定位文档（不存 kbId —— 库 id 随环境变，标题不随）；
  `expectChunks` 是该文档内的期望片段，每项含 `index`（chunkIndex）与
  `snippet`（该片段开头 ≥8 个字符的**内容指纹**，V2 用）；
  `answerMustContain` 是答案层人工抽检用的关键词锚点，**允许为 null**
  （null 表示"这个 case 只验检索层"，见 V8）。
  跑 `node scripts/eval.mjs --check`：校验
  ① id 唯一、question 非空、expectChunks 非空且 index 为非负整数；
  ② **`documentTitle` 必须恰好匹配到 1 个文档**（0 个或 >1 个都报错，V11）；
  ③ `answerMustContain` 为 null 的 case 数 **≤ 总条数的 1/3**（V8：允许纯检索
  case，但不允许整份评测集都放弃答案层）；
  全部通过时打印 `OK: <N> cases`。
- 怎么验（**必须做反证**）：故意删掉一条的 `expectChunks` → 再跑 `--check`
  → 必须报错且**指出第几条缺哪个字段**，退出码非 0。恢复后再跑。
  再做一个同名反证：把某条的 documentTitle 改成库里不存在/重复的标题 →
  必须报"匹配到 0 个 / 2 个文档"（V11）。
- 不通过意味着：评测集没有 schema，字段写错脚本静默跳过，
  评测出来的每一个数字从根上就不可信。

**A2 期望片段的标注是准确的** ⭐ 尺子不能歪
- 判绿：**首次建立评测集时必须 100% 全量核对**（15 条左右，一次半小时内可完成）；
  之后每次新增/改动 case，只需核对**新增与改动的那几条**。
  核对内容：该 `index` 的 chunk content 是否**确实包含该问题的答案**，
  且 `snippet` 是否是该 chunk 的开头原文。
- 怎么验：**固定抽 3 条复检**（不随机、不凭眼缘，避免"挑好验的验"）：
  ① `expectChunks` 条数最多的那条；② 按 id 排序第 3 条；③
  `answerMustContain` 为 null 的那条（若有）。用 db-query 查 chunk content
  逐字对照，记录写进 `eval/RESULTS.md`。
- 不通过意味着：标注错了，recall@5 的分数越高越骗人。
  **评测集是尺子；这条不过，C 组的"调优前后对比"全部作废。**

**A3 评测集与文档内容的耦合被显式声明 + 越界与漂移检测**（V2）
- 判绿：① `eval/RESULTS.md`（或 cases.json 顶部注释）注明：
  "本评测集依赖 C 手册当前版本的分片结果；重新索引或更换文档后必须重跑
  A2 的核对"；
  ② `--check` 增加两条校验：
  **越界**——`max(expectChunks[].index)` 必须 < 该文档实际 chunk 数；
  **漂移**——该 index 的 chunk content 必须以 `snippet` 开头，
  否则报"标注已过期：c07 的 chunk 4 开头是「XXX」，期望「培训基金」"。
- 怎么验：两个反证 —— ① 把某条 index 改成 999 → 报越界；
  ② 把某条 snippet 改成一个不存在的词 → 报漂移。
- 不通过意味着：**只比数量是不够的**。改一次切片分隔符，chunk 数可能仍是 9，
  但第 4 块的内容已经换了 —— 没有指纹就只能发现"少了一块"，
  发现不了"每块都错位了"，评测会静默地测一堆错段落。

## 三、B 组：评测脚本

**B1 一条命令跑完全流程**
- 判绿：`node scripts/eval.mjs` 逐条打印每个 case 的
  `id / @1 / @3 / @K / hit（命中数/期望数）/ expect / topK 的 chunkIndex 序列`，
  最后三行分别打印 `TOTAL recall@1 / @3 / @K`，再一行 `(N cases)`。
  默认**不调 LLM**。
  ⚠️ **stdout 里不得出现任何随时间变化的内容**（耗时、时间戳、随机 id），
  **也不得出现相似度小数**（`--verbose` 才打印）——
  耗时打到 stderr。这是 B3 的前提（V4/V12 同源）。
- 怎么验：真跑一遍，肉眼核对输出含上述全部字段；总条数 = cases.json 条数；
  另跑一次 piped 到文件，检查文件里没有形如 `1234ms` / `2026-10-26T` 的片段。
- 不通过意味着：评测不能一键复现，就退化成"每次手工点一遍"，
  C 组的对比回路建立不起来；而带耗时的输出会让 B3 永远失败。

**B2 三个 K 的口径钉死、排序确定、且与源码对齐**（V4 + V10 + V13）
- 判绿：
  ① K 的取值：检索仍取 `TOP_K`（与线上同源）；**计分同时报 @1 / @3 / @5**。
  原因见 V13：库里只有 9 块时 @5 覆盖 55%，实测基线 25 条**全中 = 1.000**，
  任何调优都测不出差异（天花板效应）。@1（实测 0.740）与 @3（0.960）
  才有区分度。@K 仍必须报 —— 它是与线上对齐的那个数。
  ② **recall@k 按"位置"算**：一个期望片段排在召回序列的第 4 位、
  但前 3 位里有 2 个来自其他文档的片段，它在 @3 里就算没进
  （实现：记录每个期望块在 hits 里的首次下标，`下标 < k` 才算命中）。
  按"进没进前 k 条"来算会系统性高估。
  ③ 多期望片段按 **命中数/期望总数** 计分（不是命中任一即满分）。
  ④ SQL 排序必须带**确定性的二级排序**，而且排序键要先**归并到测量噪声以下**
  （V4 → V17）：`order by round((embedding <=> $1)::numeric, 3) asc,
  "chunkIndex" asc`。只写 `"chunkIndex" asc` 不够 —— 它只在相似度**完全相等**
  时生效，而远程 embedding 的抖动可达 1e-3（实测 c18 第 4/5 名顺序在两次
  运行间翻转、三指标与命中数全同）。round 到 3 位 = 正式承认
  "差异小于测量噪声"的两块并列，再由 chunkIndex 定序。
  **确定性是构造出来的，不是碰巧的。**
  ⑤ `--check` 必须**打印当前生效的 K 及其来源**（`src/lib/retrieve.ts` 的
  `TOP_K`）。⚠️ 注意这不是"比对"——脚本的 K 本来就读自 retrieve.ts，
  自己跟自己比永远一致（V10 二次修订：第一版就是这么写的，反证时把
  `TOP_K` 改成 4 依然全绿，属于同义反复的空转检查）。**看得见 > 查一遍。**
  ⑥ **召回深度必须独立于线上 K**（V14）：SQL 的 `limit` 取 `max(5, K)`，
  而不是 `K`。否则一旦把 `TOP_K` 改成 3，召回只剩 3 条，`@5` 自动退化成
  `@3` —— 指标口径跟着参数一起变，C2 的"改前/改后"就变成"口径变了"，
  归因直接失效（实现期实测：改 K 前不修这条，@5 仍打印 1.000 但意义上已不同）。
  线上实际只用前 K 条，所以 K<5 时额外打印一行 `recall@K（线上生效口径）`。
- 怎么验：反证 —— 临时把 `retrieve.ts` 的 `TOP_K` 改成 4（**别提交**），
  跑 `--check` 输出必须变成 `K=4（来源 …）`（不是报错，是让人看见）；
  改回 5 后恢复 `K=5`。
  位置口径的验证：取一条 expect 2 个片段、实际只有 1 个进前 3 的 case，
  脚本必须打印 `@3=0.50` 而不是 `1.00`（基线里的 c19 就是这种）。
- 不通过意味着：口径含糊时，"分数变了"无法解释是检索变好还是口径变了；
  排序不确定时，同一次评测跑两遍结果不同（B3 挂），归因彻底失效。

**B3 确定性：连跑两次的**排序与总分**必须一致**（V12 修订）
- 判绿：同一数据库状态下连跑两次 `eval.mjs`，两次的**逐条 `top5` 索引序列与
  `TOTAL recall@5`** 完全一致（diff 为空）。
- 怎么验：`node scripts/eval.mjs > r1.txt && node scripts/eval.mjs > r2.txt`
  → `diff r1.txt r2.txt` 为空。
- ⚠️ **默认输出里不得包含相似度小数**（`--verbose` 时才打印）——原因见 V12：
  embedding 是远程服务，同一输入两次返回的向量浮点尾数会差最后几位
  （实测同一句问题 c19 的某块 0.593 → 0.594），相似度第 3 位小数不稳定。
  **确定性真正成立的地方是排序结果（整数序列），不是相似度小数。**
  把判据钉在"逐字节含小数"上，会让一个正确实现随机假红。
- 不通过意味着：要么排序没有 tie-breaker（B2 ② 没做），要么脚本里混进了
  非确定性环节（比如 LLM 参与判分）。这两种都是真问题，与浮点尾数无关。
- ⚠️ **适用范围仅限纯检索模式**（V16）：`--with-llm` 的输出天然不确定
  （LLM 采样未固定，实测同一配置两次 c23 一次给推断、一次拒答），
  不能拿它来验 B3。答案层比对的稳定性由 C4-b 的"稳定性前置"单独管。

**B4 纯检索评测的耗时有上限**
- 判绿：默认模式（不带 `--with-llm`）全量跑完 **< 60 秒**
  （N 个 case 主要是 N 次 embedding API 调用 + N 次查询，秒级才正常）。
- 怎么验：跑的时候看一眼耗时并记录。
- 不通过意味着：评测脚本里混进了重量级环节（逐 case 重新索引全库之类），
  评测从"随手跑"变成"专门排期"，C 组"一次改动跑一次"的节奏就维持不了。

**B5 失败不静默：单 case 出错要让整体退出码非 0**
- 判绿：任何一个 case 检索报错（如 embedding API 挂了、文档定位不到）时，
  脚本打印明确的错误行（含 case id 与原因），**最终退出码非 0**，
  且总分打印为 `TOTAL: FAILED (N errors)`，绝不带着错误算一个分数出来。
- 怎么验：反证 —— 临时把某条 case 的 documentTitle 改成不存在的标题 →
  跑脚本 → 报错定位到该 case，`echo $?` 非 0。改回。
- 不通过意味着：API 抽风的那次评测算出一个残缺分数被当成基线记进
  RESULTS.md，后面的所有对比都建立在这个坏基线上。

## 四、C 组：调优有效性

**C1 基线数字在案，且环境快照完整**（V5）
- 判绿：`eval/RESULTS.md` 的基线一节必须同时记录**四样东西**：
  ① 参数（TOP_K / 切片目标 / 重叠 / prompt 版本）；
  ② **文档集合快照**（每个 `documentTitle` + chunk 数）；
  ③ **embedding 模型名与调用日期**（如 `BAAI/bge-m3`，2026-10-26）；
  ④ 三个指标（@1 / @3 / @K）+ 逐条分数。
  且任何人重跑 `eval.mjs` 能复现同一组总分（B3 兜底）。
- 怎么验：把 RESULTS.md 的基线节贴给一个没参与的人看，问"你能不能判断
  这份分数还能不能跟今天的结果对比" —— 四样缺任意一样就答不出来。
- 不通过意味着：换了 embedding 模型、加了一份文档、或者改了切片之后，
  旧分数看起来还在，但它和新分数**不是同一把尺子量出来的**。
  这类"伪对比"比没有基线更危险：它会让人得出相反的结论。

**C2 一次单参数改动 + 前后对比（且改动必须落在指标能观测到的范围内）**（V1 + V3）
- **前置条件（V1，不满足则本条判据无效）**：若改动涉及**切片或嵌入**
  （切片目标长度、重叠、分隔符、embedding 模型），必须先对被测文档
  **全部重建索引**，并确认 `--check` 的 chunk 数与漂移校验通过，
  再跑评测。否则跑的是"新参数 + 旧 chunk"——测的不是你改的东西。
- 判绿：改动**恰好一个**参数，且该参数必须能被 recall@5 观测到：
  `TOP_K`、切片目标长度、重叠、分隔符、embedding 模型，**五选一**。
  （V3：**prompt 类改动不适用本条** —— recall@5 只看检索层，
  改 prompt 分数必然纹丝不动，用它来"验证调优有效"是自欺。
  prompt 改动走 `--with-llm` 人工对照，见 C4-b。）
  改动前后各跑一次全量评测，`eval/RESULTS.md` 增加一节：
  改了什么 / 前置重建索引与否 / 前后总分 / 逐条升降 / 一句话结论。
- 怎么验：RESULTS.md 里能一眼对出"改动项 → 两组数字"；改动项之外
  （其他参数、文档内容、评测集）没有任何变化 —— 否则不满足决策③。
- 不通过意味着：一次改多个变量，分数变了也不知道归功/归罪于谁；
  或者改了切片却没重建索引，得出的"变差/变好"完全来自测量错位。

**C3 每一次尝试都有记录；凡变差必须回滚并写原因**（V6）
- 判绿：`eval/RESULTS.md` 里**每一次**参数尝试都有记录（无论升降），
  格式固定四列：改动项 / 前后总分 / 逐条变化 / 处置（保留/回滚 + 理由）。
  **凡判为变差的那次，参数必须已回滚**（`git diff` 可见参数回到基线值），
  且理由写清楚。
- 怎么验：对每一条"变差"记录，检查当前源码里的参数值 = 基线值。
- 不通过意味着：调优记录里只有"改了都变好"，要么根本没试过第二个方向，
  要么试了但没记 —— 两种情况都说明这把尺子没真正参与决策。
  ⚠️ **本条不要求"必须出现一次变差"**（V6：初稿那样写等于逼首次就成功的人
  去做一次注定失败的实验来凑条目，属于典型的"正确实现被判失败"，
  而且会诱导无意义的工作量）。

**C4 调优后 W5 的敏感条目必须重测，判定标准是"不退化"**（V7 + V3-b）
- **C4-a（检索参数改动后）**：重测 W5 的 **B1（代词追问）** 与
  **B4（常识污染）** 两条。
  判绿标准是**"不退化"**：B1 仍能答对、B4 仍拒绝用外部知识作答。
  ⚠️ 初稿写的"与 W5 验收时一致"是错的（V7）：如果改动本身让 B1 更稳
  （比如 TOP_K 从 3 提到 5），"一致"反而判失败 —— 判据不能禁止改进。
- **C4-b（prompt 类改动后）**：用 `--with-llm` 跑一遍全量，
  人工对照 `answerMustContain` 关键词，判绿是"命中数不低于改动前"，
  并把改动前后的命中数一起记进 RESULTS.md。这是 V3 的配套出口：
  prompt 的改动在 recall@5 里看不见，只能在这一层验。
  **前置（V16，必须先做，否则对比是噪声）**：
  ① 同一配置连跑两次 `--with-llm`，两次命中数必须**相同**。
  实测当前不满足 —— `temperature` 从未显式设置（走服务端默认），
  同一配置两次跑，c23 一次答"未满 4 年折旧期，暂不能申请更换"、
  一次答"文档中没有相关内容"（关键词都命中，但质量不同）。
  → 未固定采样参数前，C4-b 的"改动前后命中数"差异无法区分
  "prompt 起作用了"和"这次抽到了另一种说法"。
  ② 固定方式：在 `llm.ts` 与 `eval.mjs` 的请求体里同时写死同一个
  `temperature`（线上与评测必须一致，否则测的不是线上行为），
  再重跑①直到两次一致。
  ③ 对比取**两次取样的较差值**（保守），不取较好值。
  **④ 判定的只能是"关键词命中数"，不能是字面或单条质量**（V18）：
  实测 `temperature=0` 后同配置连跑两次，25 条里仍有 6 条措辞不同、
  c23 的结论甚至在"未满折旧期不能换"和"文档中没有相关内容"之间摆动。
  → 命中数稳定（两次都 25/25）可用；"某条答得好不好"不稳定，不能当判据。
  **⑤ 若同一次实验里既动了 prompt 又动了 sampling，则该实验作废**：
  先单独固定 sampling 并证明命中数稳定（前置轮），再单独改 prompt（对比轮）。
  两轮混在一起，"星号消失"到底归 prompt 还是归采样，永远说不清
  （本次就是这么做的：对照轮 v1+temp0 仍有 3 处星号，改 prompt 后 0 处 —— 归因才成立）。
- 不通过意味着：改检索参数最伤的就是"多片段覆盖"与"零信息量追问"这两类
  （TOP_K 变小直接砍掉追问的上下文来源），而这两类问题评测集的
  recall 分数**反映不出来**（它只看期望片段在不在 TOP_K 里，不看
  LLM 拿到上下文之后用没用对）—— 所以必须手测兜住评测指标的盲区。
  **这条是"评测不是万能"的显式声明。**

## 五、D 组：边界与回归

**D1 评测脚本对线上数据零写入**
- 判绿：跑完评测前后，库里五张表（KnowledgeBase / Document / Chunk /
  Conversation / Message）的**行数与 `max(updatedAt)` 全都不变** ——
  评测只读。（为什么要看 updatedAt：只查行数发现不了"脚本误 update 了一行"，
  这类写入最隐蔽，也最容易在演示前把数据改花。）
- 怎么验：跑前跑后各跑一次：
  `select 'kb',count(*) from "KnowledgeBase" union all select 'doc',count(*) from "Document" union all select 'chunk',count(*) from "Chunk" union all select 'conv',count(*) from "Conversation" union all select 'msg',count(*) from "Message";`
  两次数值逐行相同。
- 不通过意味着：评测会污染用户数据（哪怕只是多写一行"评测"标记），
  这套脚本就永远不能在生产库上跑，W7 之后直接作废。

**D2 评测集覆盖面有下限（人工登记，不靠估算）**（V9）
- 判绿：
  ① ≥15 条问题覆盖 C 手册**至少 3 个不同章节**，且期望片段分布在
  **至少 5 个不同 chunkIndex** 上；
  ② **章节归属由人工在 `eval/RESULTS.md` 里逐条登记**（case id → 章节名），
  不用 chunkIndex 去"近似推断"（V9：初稿那句"按 chunkIndex 分布近似"
  无法证伪 —— 近似到几算过？谁来判断？不可证伪的判据等于没写）；
  ③ 必须包含两类刻意构造的 case：
  - **多片段 case**：`expectChunks` ≥ 2，用来兑现 B2 的 recall 梯度。
  - **跨片段组织 case**（V9：初稿"答案关键词与检索片段分离"表述含混，
    这里给可构造的定义）：问题的答案**需要把两个不同 chunk 的信息
    合并/比较才能得出**，`expectChunks` ≥ 2，且 `answerMustContain`
    里的关键词**不出现在任何一个单独 chunk 的原文里**（比如手册里
    分散写着两项额度，问题问"两项相差多少"）。
    这条同时证明"检索命中 ≠ 答案正确"——两层判分确实各管一层。
- 怎么验：`--check` 输出覆盖统计（章节数由登记表提供，chunkIndex 分布自动统计），
  与该 case 的关键词逐个 grep 各 chunk 文件确认"不出现在单个 chunk 内"。
- 不通过意味着：20 个问题全打在一个章节上，recall 总分虚高，
  单参数调优在这种窄样本上的升降完全可能是噪声。

**D3 W5 十九条中自选三条回归（跨组，不许全挑同一组）**
- 判绿：从 W5 的 19 条里挑出**你认为改动最可能破坏的 3 条**，
  三条必须来自**至少两个不同的组**（A/B/C/D/E），写明每条的挑选理由并实测通过。
- 怎么验：挑选理由写进 RESULTS.md（一行一条即可，格式："选了 C3，因为…"）。
- 不通过意味着：要么无脑挑最简单的三条（那就失去回归的意义），
  要么漏掉了真正被破坏的条目。**这条考的是判断，不是体力。**
  （出题人提示，剧透一半：本轮改动集中在切片与检索参数，
  上下文拼装和消息持久化没动 —— 挑选理由必须和这个改动面自洽。）

## 六、Out of Scope（明确放弃）

- LLM-as-judge 自动答案评分（引入第二个模型的不确定性，20 组规模不值得）
- 多模型 / 多 embedding 对比评测
- 评测看板、报表、CI 集成
- 压测与并发评测
- 评测集的自动生成（问题必须人工写，自动生成的问题质量不可控）

**三条实现提示**（写代码前想清楚，别写到一半再回头）：
1. `eval.mjs` 的检索部分**复用 `verify-retrieval.mjs` 的套路**：
   fetch 调 SiliconFlow embedding → pg 客户端 SQL
   `order by embedding <=> $1 asc, "chunkIndex" asc limit K`
   （二级排序不是可选项，见 B2 ②）。
   不要 import `src/` 下的 TS（脚本是 mjs，复刻这两段即可，
   这是"验证脚本零依赖"惯例的延续）。
2. `--check` 与正式评测分开：check 只读 cases.json + 查库 + 读
   `retrieve.ts` 源码做 K 对齐（B2 ③）；评测才调 embedding API。
   check 失败就直接退出，不进评测。
3. `--with-llm` 复用 `verify-chat.mjs` 的调法（注意 thinking 关闭参数），
   输出"问题 / 生成答案 / answerMustContain 逐个关键词的命中行"，
   人工抽检看这个输出就够，**不要**在脚本里做自动判分。
