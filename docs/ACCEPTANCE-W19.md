## 0. 这个 W 不是「加一张表」

现状的租户边界就是**用户本人**：

```
KnowledgeBase.userId  →  谁能访问这个库
Conversation.userId   →  谁能看这个会话
```

加一张 `Organization` 表、给业务表加个 `orgId` 字段，一天就能做完。**但那不是这个 W 的难点。**

真正的难点是三条，每条都不会报错：

**① 漏一处 is 不报错的。**
`where: { id, userId }` 里少写一个条件，功能照跑、151 条单测照绿、`tsc` 零错误、
lint 零 error —— 但 A 组织能读 B 组织的库。多租户的头号事故从来不是"加密不够"，
是**某一次查询忘了带租户条件**。它没有任何信号。

**② 存量数据要迁，而迁移不可回滚。**
线上有 2 用户 / 9 库 / 13 文档 / 63 块 / 17 会话 / 97 消息。把这些挂到"每人的默认组织"上，
一次做错就得手工修数据。而迁移脚本本身**没有第二次机会**：跑过一次，脏数据就在那儿了。

**③ 配额必须原子扣减（W21 的前提）。**
这一周先把 `UsageRecord` 的位置想清楚，不做实现 —— 但数据模型要留出位置，
否则 W21 又要改一次表。

所以本周的产出不是"能建组织了"，是：**一套让越权无法静默发生的结构 + 一组证明它没发生的测试。**

### 1.1 隔离面

| 形态 | 处数 | 位置 |
|---|---|---|
| `where: { …, userId }` 查询条件 | **15** | `kb/actions.ts`、`kb/[id]/actions.ts`、`kb/page.tsx`、`kb/[id]/page.tsx`、`history.ts` |
| `const userId = await requireUserId()` | **9** | 同上 + `api/kb/[id]/chat-agent/route.ts` |

**关键事实：隔离写法已经收敛成单一模式。** 15 处全是 `where: { …id, userId }` 的形状，
没有第二套。所以这次改造可以**逐处枚举、逐处审**，而不是"上去改一遍看看会不会炸"。

这一点值得记住：**能安全做结构性重构的前提，是现状已经收敛。**
如果 15 处各写各的，同样的改造就只能靠人肉记忆，风险高一个数量级。

## 2. 设计决策

### D1：`orgId` 是权限字段，`createdBy` 是归属字段——两个都留

不是把 `userId` 改名成 `orgId`。后者会丢掉"这个库是谁建的"。

| 字段 | 语义 | 谁用 |
|---|---|---|
| `orgId` | **能不能访问** | 所有 where 条件 |
| `createdBy` | **谁建的**（审计） | `/admin`、未来的"仅创建者可删"规则 |

一个字段同时承担两件事，是这类改造最常见的坑：等到要做"成员能看不能删"时，
才发现没有字段能回答"谁建的"，只能回头加一次迁移。

### D2：不上 Prisma client extension 做自动租户过滤

主流方案是给 Prisma 挂个 middleware/extension，自动往每个 `where` 里注入 `orgId`。
**这个项目不能用，理由是硬性的**：

> 本项目的向量检索必须走 `$queryRaw`（Prisma 不支持 `vector` 类型的表达式查询，
> 见 `retrieve.ts` 的两段式 SQL）。**extension 管不到 raw query。**

于是就变成：98% 的查询有自动保护，剩下 2% 没有 —— 而这 2% 恰好是**最核心的检索链路**。
更糟的是它会制造一种"我们已经做了租户隔离"的错觉，让 review 时没人再逐处看 where。

**有盲区的防护比没有防护更危险。** 这和 W16 那条教训是同一类：
评测脚本手抄了一份检索 SQL，测的是线上不存在的系统 ——
**"看起来受保护"和"真的受保护"之间的差距，只有审计能发现，而错觉会让人停止审计。**

所以走显式路线：`requireOrgId()` + 每处 where 都带 `orgId` + 越权测试兜底。

代价诚实记账：58 处靠人审，所以必须有测试网，不能靠"我改的时候很小心"。

### D3：越权测试怎么造——不用两个 GitHub 账号

直觉方案是 Playwright 开两个 storageState 打真实 HTTP。**不采用**，两个原因：

1. 两个 GitHub 账号的登录态是外部状态，会过期，进不了 CI（W13 已经定了"门禁只放稳定可复现的东西"）
2. 它测的是"路由层有没有把请求挡住"，挡不住"某个 Server Action 内部少写了一个条件"

改用 **DB 集成测试直打查询层**（`RUN_DB_TESTS=1`，与现有 db 测试同一档）：

- 造两组互相独立的数据：orgA（用户 A、库 A、文档 A、会话 A）、orgB（同构）
- 用 **A 的身份**执行 10 类操作，断言**全部拿不到 B 的东西**
- **同时断言 A 能正常操作自己的东西**

最后那条是重点。只测"打不进去"，会得到一个"所有查询都返回 null"的假通过 ——
把 `orgId` 写死成一个不存在的值，10 条全绿，功能全废。
**必须成对断言：该挡的挡住了，该通的通着。**

### D4：迁移用「默认组织 + 回填」两步，不用一次 SQL 做完

1. 给每个存量 `User` 建一个 `Organization`（名字 `{name} 的空间`），并建 `Membership`（role=owner）
2. 回填 `KnowledgeBase.orgId` / `Conversation.orgId`（按 `userId` 对到默认组织），`userId` → `createdBy`
3. 最后才把 `orgId` 设为 NOT NULL

分三步的理由：中间任何一步失败都能停在那、重跑（每步幂等），而不是一个事务里赌全部。
线上数据量小，但方法要对——**数据量小的时候练对方法，比数据量大的时候救火便宜。**

## 4. 显式不做（这一周）

- **邀请链接**（W20）：owner 生成一次性 token，对方登录后加入
- **角色细分**（W20）：现在只有 `owner`，W20 加 `member` 与权限矩阵
- **配额与用量**（W21）：`UsageRecord` 表结构这周先留位置，不做扣减逻辑
- **组织改名 / 删除 / 转让**：等角色做完才有意义
- **API key**：程序化访问，排在配额之后（它需要一个"代表组织"的凭证模型）

写在这里是为了防止这周三心二意 —— 多租户最容易失控的方式，就是第一周就想把邀请、
权限、计费一起做完，结果每一样都只做了 60%。

## 5. 实施记录

### 5.1 迁移

**手写 SQL，不靠 `migrate dev` 生成。** 自动生成的会是
`ADD COLUMN "orgId" TEXT NOT NULL`（表里有数据 → 必然失败）+ `DROP COLUMN "userId"`
（回填之前就删 → 数据没了）。正确顺序 Prisma 猜不出来：建表 → 加可空列 → 回填 → 断言 → 收紧。

**先遇到一个拦路虎**：`migrate dev` 报 W17 那个 migration 的 checksum 与实际记录不符，要求 **reset 整个库**（会清空线上数据）。
先 `prisma migrate diff --from-config-datasource --to-schema` 证明「库结构与 schema 的差异只有本周新增」，
确认那个文件虽然被改过、**结构是对的**，才去修正 `_prisma_migrations.checksum`。
顺序不能反：先证明一致，再对齐记录；先改记录等于把「文件被改过」这件事藏起来。

迁移前 dump 了 6 张表到 `.backup/w19-before/dump.json`（`.backup/` 已 gitignore）。
迁移是 DROP COLUMN，**没有第二次机会**。

### 5.3 边界改造（C3）

`userId` 相关处数：**58 处 / 10 个文件** → 业务查询全部换成 `orgId`。

| 检查 | 结果 |
|---|---|
| `npm run check:scope` 扫描 | 51 个文件，命中 30 处业务查询 |
| 带租户条件 | **17** |
| 白名单（逐条写理由） | **13** |
| 裸查询（既无条件也不在白名单） | **0** |

白名单不是"暂时放过"。每条都写了为什么安全，比如 `conversation.update`（只更 `updatedAt` 让会话冒泡，id 来自已校验的 `resolveConversation`）、
`document.update`（按刚 `create` 出来的 id 更新索引状态，客户端碰不到）。

**`$queryRaw` 是这套检查的盲区**，脚本里显式声明了：向量检索必须走原生 SQL，那一层的边界在调用方 ——
`retrieve(kbId, …)` 的 `kbId` 由路由 `findFirst({ id, orgId })` 校验后才传入。

### 5.4 越权测试（C4）：27 条

| 分组 | 条数 | 断言 |
|---|---|---|
| 拿 A 的身份打 B 的资源 | 12 | 全部拿不到（列表/详情/改名/删库/上传/读文档/删文档/重建索引/会话列表/读会话/删会话/续问） |
| 反证（阴性对照） | 2 | 不带 `orgId` 时 B 的数据确实存在 —— 证明上面 12 条不是因为"数据压根没有"才通过的 |
| A 对自己的资源 | 6 | 全部正常（含真代码 `loadConversationMessages` / `resolveConversation`） |
| **同组织第二个成员 C（role=member）** | **7** | A 建的库/文档/会话 C 都看得见；C 建的会话 A 也看得见；C 仍打不进 B |

第四节是**补上去的，原本漏了**。理由值得记：只测"挡得住别人"会得到最坏的一种假绿 ——
把 `where` 里的 `orgId` 写成 `createdBy`，前三节 21 条**全部照样通过**（跨组织确实拿不到、
A 拿自己的也确实拿得到），但产品已经废了：拉人进来什么都看不见，多租户退化成单人租户。

**所以做了一次变异测试**：把 `loadConversationMessages` 的 `where: { id, orgId }` 改成
`where: { id, createdBy: orgId }`（这类 bug 最真实的形态），跑测试 —— **2 条失败**，
其中一条正是新增的「C 能打开 A 的会话」。改回来，27 条全绿。
不做这一步，"27 条全绿"只是一句话；做了才知道它绿是因为对的写了、错的会被抓住。
