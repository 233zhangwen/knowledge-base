## 一、三个决策（先定，否则判据无从写起）

### 决策① 历史存 **citations 快照**，不存外键

**结论**：`Message.citations` 存完整的 `Citation[]`（含片段全文 content），不存 `chunkId` 外键。

推理链：
- 我们在 W4 已经拒绝过一次"前端二次查库"（B2）。历史里的引用如果只存 `chunkId`，
  用户三个月后点开，查到的是**当前**库里的 chunk —— 而那期间文档可能已被删、已被重建索引、
  切片已重排。**这就是同那个 bug，只是延迟了三个月发作。**
- 反过来说，存快照的代价是每条 assistant 消息多几 KB JSON。按一个会话 20 轮算，
  几 MB 而已，Postgres 免费层完全无所谓。**空间换正确性，这里很划算。**
- 副作用（必须写进 README）：重建索引或删文档后，历史回答里的引用仍然显示当时的原文。
  这是**特性不是 bug** —— 它忠实记录了"这个答案是依据当时那份文档得出的"。

### 决策② 多轮上下文带 **最近 3 轮（6 条消息）**

**结论**：`take 6`，且**历史消息只带 content，不带它们自己的 citations。**

推理链：
- 预算估算：一条 assistant 回答约 800 token、用户问题约 50 token，一轮不到 1000。
  3 轮 ≈ 3000 token；system prompt + 5 个 chunk（约 2500 字 ≈ 1800 token）；合计 **5k 上下**，
  DeepSeek 上下文绰绰有余。**瓶颈不是窗口，是注意力稀释**（W4 决策①同一个道理）。
- 为什么历史不带 citations：一条回答的 5 个片段 ≈ 2500 字，带上历史引用等于把上下文再翻一倍，
  而那些旧的检索结果跟当前问题大概率无关 —— 典型的"花了钱还变差"。
- 3 轮这个数字是**可调常量**，不是架构决定。发现追问经常被截断，改成 5 是改一个数字。

### 决策③ 用**会话分组**代替分页

**结论**：侧栏列出该知识库下**最近 20 个会话**，点开加载该会话的消息。不做滚动分页。

推理链：
- 会话本身就是天然的分组边界 —— 一次会话的消息量天然有上限（很少超过 30 条），
  **不需要分页就已经解决了"数据量无限增长"的问题**。这是用数据模型解决性能问题，不是用套路。
- 真要做分页是 W6 的事。MVP 阶段一个知识库有 20 个以上会话才会碰到，到时候再说。
- 会话标题：取**第一条用户消息的前 20 个字**，不调 LLM 生成摘要。
  理由：标题只是个导航锚点，为它花一次 LLM 调用不值；而且摘要会引入延迟，首轮体验变差。
- ⚠️ 这个"20 个"由 **A6** 验收（最初的 spec 声明了它却没有任何判据，属于
  "既没验收也没声明放弃"，修订时补上）。

## 二、A 组：持久化

**A1 刷新不丢**
- 判绿：提一个问题 → 等答案生成完 → **按 F5 刷新页面** → 刚才的问答原样出现在消息列表里，
  顺序正确（用户在上、助手在下），不需要任何额外操作。
- 怎么验：浏览器手点，刷新前后截两张图对照；再跑
  `node scripts/db-query.mjs 'select c.title, count(m.id)::int from "Conversation" c join "Message" m on m."conversationId"=c.id group by c.id;'`
  确认 `count = 2`（一问一答）。
- 不通过意味着：消息只在前端 state 里，没真正落库。这是"看起来能用、一刷新就傻"的典型。

**A2 落库顺序：user 先 assistant 后**
- 判绿：请求到达时立刻落 user 消息，流**全部结束**后再落 assistant 消息。
- 怎么验（**不许靠手速抢时间**，那不是判据，是抽奖 —— 用确定性事件）：
  ```bash
  # 绕开浏览器直接打流式接口，收到头几个字就 Ctrl+C
  curl -N -X POST http://localhost:3000/api/kb/<kbId>/chat \
       -H 'Content-Type: application/json' -d '{"question":"把所有条款总结一下"}'
  ```
  中断后立刻查库：
  `select role, count(*)::int from "Message" group by role;`
  必须是 **user=1、assistant=0**。
  （等价手段：答案吐到一半时把 dev server 进程 kill 掉，或直接关代理断网 ——
  目的是制造一个"流被中断"的确定状态，而不是去抓一个转瞬即逝的中间态。）
- 不通过意味着：要么两条一起写（那用户的提问在崩溃时丢了 —— 用户回来看到的是
  一个空会话，连自己问过什么都不知道），要么 user 也没写。

**A3 citations 快照：删文档后历史引用仍可读** ⭐ 本组最重要
- 判绿：① 问一个能召回片段的问题，确认答案带引用 → ② 回到文档列表，**删除那个文档**
  （连带 chunks 一起没了）→ ③ 刷新页面回到刚才那个会话 →
  **那条历史回答的引用仍能点开，仍然显示当时的原文片段**。
- 怎么验：删除前后的 `select count(*) from "Chunk"` 对比（应减少），
  再对比历史引用里显示的文本与删除前截图是否一致。
- 不通过意味着：存的是外键而不是快照 —— **W4 的 B2 那个坑在历史维度上重犯**。
  这条挂掉的话，所谓"可溯源"在隔夜之后就不成立了。

**A4 会话标题自动生成**
- 判绿：新会话问"年假有多少天" → 侧栏该会话标题变成这几个字（超过 20 字截断加省略号）。
  **不触发任何额外的 LLM 调用**（用 dev 终端的 `[chat]` 日志行数核对：一次提问只有一行日志）。
- 怎么验：看侧栏文字 + 数 dev 日志里 `[chat]` 出现次数。
- 不通过意味着：可能为标题偷偷调了 LLM —— 首轮多花几百毫秒和一个请求的钱，换一句废话。

**A5 新会话的 id 能回到前端；生成途中刷新能找回会话**
- 背景：按 D2，会话是**第一次提问时才由服务端创建**的，而响应是**流式**的 ——
  所以新会话的 id 必须通过流协议（或独立字段）回到前端，否则前端永远不知道这次会话的 id。
- 判绿：
  ① 首次提问后，侧栏/历史里能定位到这次会话（拿到 id），再提问一次能接着聊（不再新建会话）；
  ② **答案还在流式生成时按 F5** → 刷新后仍能回到刚才那个会话，能看到自己那句提问，
  会话标题不为空（若是"未命名"也要能一眼认出是自己刚才那次).
- 怎么验：第 ① 步用
  `select id, title, count(m.id)::int from "Conversation" c join "Message" m on ... group by c.id`
  确认连续两次提问落在**同一个** conversationId 下；
  第 ② 步看侧栏最新一项是不是刚才那句提问的前 20 字。
- 不通过意味着：要么 id 没透传（每次提问都新建一个会话，历史被撕成一地碎片），
  要么 id 只在流结束时才给（中途中断/刷新就成了孤儿会话 —— 用户点进去看到自己问了句什么，
  下面永远是空的，且永远等不到答案）。
  **这条现在是"没想过"，必须变成"想过并决定接受某个行为"。**

**A6 会话列表上限 = 20**
- 背景：决策③ 声明"侧栏列出最近 20 个会话"，但原 spec 没有任何一条验证它 ——
  那就落进了最糟的状态：**既没验收，也没声明放弃**（W3 的漏洞 2 是同一类）。
- 判绿：在该知识库下造 **25 个会话**（脚本批量 insert 即可）→ 侧栏显示 **20 个**，
  且**按最近更新排序**、丢掉的是最老的那些；点开任意一个仍能正常加载消息。
- 怎么验：数侧栏条目数；再点最后一个确认能打开。
- 不通过意味着：要么没做上限（聊几个月后首屏拉几百个会话，页面卡死），
  要么做了但排错序 / 截断方式错（丢掉了最新的，用户找不到刚才那次对话）。

## 三、B 组：多轮上下文

**B1 代词追问能被接住** ⭐ 多轮的唯一价值就在这

> **前置条件（不满足这条，下面的判据全部失效）**：被测文档的切片数必须 **> TOP_K(5)**，
> 建议 ≥ 8 块（约 3000 字以上）。
> 理由：fixture 那两份 1400 字的文档只有 3~4 块，`TOP_K=5` 会**全量召回** ——
> 无论有没有上下文，包含答案的那块必然被喂给模型。那样这条判据验的是"检索命中"，
> 不是"上下文生效"，零上下文也能通过。（这个坑 W4 分库测试时出现过一次，这里复发。）
>
> **现成夹具**：`kb-fixtures/C-星海科技员工手册-完整版(B1专用).md`（3530 字去空白字符，
> 实测 `splitText` 切出 **9 块**，大于 TOP_K=5）—— 单独传进一个知识库即可，
> 不要和 A/B 两份混在一个库里（混了就凑不够 >8 块的"单文档"筛选条件）。
> 该文档第三节是刻意写的**年度额度降序对照表**，专供零信息量追问：
> Q1「年度额度最高的是哪一项？」→ 8000 元培训基金；
> Q2「**那第二多的那项呢？**」（不含任何文档名词）→ 必须答 3000 元团队建设费。

- 判绿：在同一个会话里连续问两句 ——
  第一句："星海科技员工手册里，正式员工年假有多少天？"（答 17 天）
  第二句（**零可被检索的信息**：不含任何文档里出现过的名词）：
  "**那第二多的那项呢？**" 或 "**后者的一半是多少？**"
  第二句的答案必须建立在上一轮的答案之上（指向病假条款 10 天 / 年假的一半 8.5 天），
  **不得**回答"文档中没有相关内容"，也不得答回年假本身。
- 怎么验：
  1. 肉眼判 + 确认该次检索的 top1 相似度明显偏低（追问句本身几乎检索不到任何东西）；
  2. **必须做反证**：临时把上下文取数改成 `take 0`，重启，重问同一句 ——
     **此时必须答不上来**（回"文档中没有相关内容"或答错）。
     如果零上下文仍然答对，说明追问句里混进了可检索的关键词，这条判据作废，
     要换一句更干净的。（套路同 A1 的反证：**证明是上下文拦住的，不是碰巧检索到的**。）
- 不通过意味着：上下文没拼进去，或者拼进去了但顺序错（历史必须在**当前问题之前**）。
  这条不过，所谓"多轮"就只是"能连着问"，跟 ChatGPT 网页版里新开一个窗口没区别。

**B2 上下文窗口上限 = 6 条**
- 判绿：在同一会话连续问 **5 轮**，第 5 轮时发给模型的消息里，
  **最早那一轮的上下问答必须已经不在上下文里**。
- 怎么验：让 `llm.ts` 在拼装后打印一行 `[llm] 上下文 N 条`（W5 要加这个日志），
  第 5 轮时 N 应该稳定在 6（3 轮历史）+ system + 当前 user，不再增长。
  **或者直接看账单/usage 的 prompt_tokens 不再随轮数线性上涨。**
- 不通过意味着：上下文无上限累积 —— 聊 50 轮之后一次请求几万 token，
  成本失控，且真正相关的当前问题被淹没。
- ⚠️ `take 6` 隐含一个前提：**历史是 user/assistant 严格成对交替的**。
  D5 允许库里存在"没有答案的孤儿 user 消息"，那会让历史变成奇数条，
  `take 6` 之后可能以一条 assistant 开头（它的问题被截掉了）或出现连续两条 user ——
  部分 OpenAI 兼容 API 遇到这种序列会直接报错。所以**先定 D5，再验这条**：
  取完之后如果首条不是 user，把它丢掉（宁可少带一轮，也不要畸形上下文）。

**B3 历史消息不带自己的 citations**
- 判绿：第 2 轮请求发出时，历史里那条 assistant 消息**只带纯文本**，
  不带它当时的 5 个片段。用法同上一条的日志佐证；也可以在 Route Handler 里临时
  `console.log(JSON.stringify(messages))` 肉眼确认 JSON 里没有多个 `参考资料` 段落。
- 怎么验：数 `messages` 里出现几次"参考资料："—— 只能是 **1 次**（当前这轮）。
- 不通过意味着：token 翻倍买来的全是噪声，且第 2 轮起答案质量反而下降。

## 四、C 组：隔离（这组的每一条都是安全事故级）

**C1 会话归属：别人的会话打不开**
- 判绿：用 A 账号的会话 id，换成 B 账号登录后访问同一个 URL → **看不到内容**，
  且接口返回 **404**（不是 403）。
- 怎么验：手头没第二个 GitHub 账号就用数据库伪造 —— 插一条 `userId='别人'` 的 Conversation，
  记下 id，然后用当前账号访问该 URL。**并且必须做反证**：
  临时去掉 Route 里的 `userId` 过滤，必须能读到那条诱饵；读不到说明诱饵根本没生效，
  前面的"绿"是假的。（W1 的 `verify-isolation.mjs` 就是这套路。）
- 不通过意味着：改一下 URL 就能看别人的全部对话记录。**这是本项目最严重的一类缺陷。**

**C2 会话与知识库的一致性**
- 判绿：把 `测试-A` 里的会话 id 拿到 `测试-B` 里去提问（改 URL 或改请求体）→ 拒绝。
  会话的 `kbId` 必须和 URL 的 kbId 一致，不一致就 404。
- 怎么验：同上。`conversationId` 由**客户端传入**，所以服务端必须自己查一次归属。
- 不通过意味着：A 库的问题可以借 B 库的会话去问，检索却发生在当前 kb ——
  历史串了、检索乱了，而且表现出来只是"答案有点怪"。

**C3 删除知识库应级联清理会话**
- 判绿：在某个知识库下聊 3 轮 → 删除该知识库 → **该 kbId 下**的会话与消息全部消失：
  `select count(*)::int from "Conversation" where "kbId" = '<被删的 kbId>';` → `0`，
  且没有孤儿 Message：
  `select count(*)::int from "Message" m left join "Conversation" c on m."conversationId" = c.id where c.id is null;` → `0`。
  ⚠️ 判据必须**带 kbId 条件**写：全表 count 回 0 只在"当前用户只在这一个库聊过"时才成立。
  把某个特定条件下的现象钉死成判据，换个场景就会误判正确实现（同 W3 的 A1 那类写法错误）。
- 怎么验：删除前后各跑一次带 where 的 count；再查孤儿 Message（外键悬空）。
- 不通过意味着：`onDelete: Cascade` 没生效 —— 用户数据删不干净，且违反"用户删了就没了"的基本预期。

## 五、D 组：失败与边界

**D1 生成失败时不写入半成品 assistant**
- 判绿：临时把 `.env.local` 里的 `LLM_API_KEY` 改错并重启 → 提问 →
  页面上显示错误提示，刷新后该会话里**只有用户那条提问，没有一条空的或半截的 assistant 消息**
  （`select count(*) from "Message" where conversationId=?` 应为 1）。
- 怎么验：数库里的行数，而不是只看界面 —— 界面可以假装清空，数据库不会。
- 不通过意味着：历史上留一堆"生成失败"的空回答，用户翻历史时看到一堆垃圾，
  而且这些垃圾在 W6 评测时会被当成样本污染数据。

**D2 未提问就不创建会话**
- 判绿：进入知识库详情页、**什么都不问**、直接刷新 →
  `select count(*) from "Conversation"` **不变**（不会因为点进页面就多一个空会话）。
- 怎么验：进页面前后各 count 一次。
- 不通过意味着：侧栏很快被几十个"新对话"刷屏 —— 用户根本分不清哪个是哪个。

**D3 长会话不崩**
- 判绿：在同一个会话里连续问 **10 轮**（超过上下文窗口 3 轮的两倍）→
  第 10 轮仍能正常出答案，**耗时不比第 1 轮明显慢**（日志里 `[chat] 总耗时` 对比）。
- 怎么验：10 轮下来总耗时曲线；同时确认第 10 轮的 `[llm] 上下文 N 条` 仍是 6。
- 不通过意味着：上下文泄漏 —— 要么 token 超限报错，要么慢到不可用。

**D4 用户主动「停止生成」时的落库语义**
- 背景：W4 已经实现了 AbortController 停止按钮。W4 时消息只在前端 state 里，停止就是丢弃；
  **W5 引入持久化之后，这个问题第一次有了语义**：用户自己按停的那半截答案，存不存？
  原 spec 一条都没写 —— 而 D1 只定义了"生成失败"，没定义"用户中止"。两者不能共用一条规则。
- 决策（写进 README，别只在验收时口述）：**中止也落库，且必须标记为未完成**。
  理由：用户是自己按停的，他知道内容不完整；历史里保留半截 + 一个"已停止"标记，
  比"刚才那几十秒白等了、回来什么都不剩"更符合直觉。
  所以 D1 的"不留半成品"只适用于**失败**，不适用于**中止** —— 这两条必须分成两个分支实现。
- 判绿：
  ① 提问后等生成到一半 → 点「停止生成」→ 答案区保留已生成的部分，并有一个可见标记
     （如"已停止"灰字 / 虚线），且不显示错误红字（用户没做错任何事，不该被当成错误）；
  ② 刷新后该条仍在库中，连带"未完成"标记一起回来。
     ⚠️ **这需要加字段**：现有 `Message` 表只有 id / role / content / citations / createdAt /
     conversationId，**没有任何"完成状态"字段**（已查过 schema.prisma），所以要补一个
     `finishReason`（`complete | stopped | failed`）并跑一次迁移 ——
     这是 W5 唯一的一处 schema 改动，趁现在想清楚，别写到一半才发现。
  ③ 紧接着再问一句，能正常继续（不会因为上一条是残缺的就让上下文畸形，见 B2 的 ⚠️）。
- 不通过意味着：要么"停止"等于"什么都不存"（用户白等），
  要么存了但没有标记（历史里一堆半截答案，用户分不清哪些是完整的）。

**D5 孤儿 user 消息在历史里必须有交代**
- 背景：这是 D1 的另一面 —— 既然失败时不写 assistant，那么**任何失败路径都会留下一条
  永远没有答案的 user 消息**。用户隔天翻回这个会话，看到自己问了一句，下面空空的，
  没有答案、没有错误说明、也没有任何线索告诉他当时发生了什么。**定义它比消灭它更重要。**
- 判绿：制造一次失败（改错 `LLM_API_KEY` → 重启 → 提问）→ 刷新 →
  该会话里那条 user 消息**不能表现得像是"发送成功但对面没回"**：
  要么带一个可见状态（如"生成失败"灰字 + 原因），要么提供「重试」入口。
  **唯独不允许的状态是：一条孤零零的提问，什么提示都没有。**
- 怎么验：库里 `select role, count(*) from "Message" where "conversationId"=? group by role`
  确认 assistant=0；界面上看那条提问有没有状态说明。
- 不通过意味着：静默失败的另一种形态 —— 用户无法区分"网络卡了"和"系统根本没工作"，
  而这正是 W2 以来我们一直在防的那类问题。

## 六、E 组：回归（W5 改了 chat 接口的入参，必须重跑）

**E1 W4 的 14 条全部重测**
- 重点四条：**B1 流式**（新加了历史拼装，最容易拖慢首字）、
  **A1 跨库隔离**（接口改造时最容易顺手删掉某个 where）、
  **B4 常识污染**（prompt 变了，规则可能被挤到后面）、
  **B2 引用一致性**（多轮之后编号容易重排错位）。
- 判绿：四条结果与 W4 验收时一致。

**E2 新会话 / 旧会话互不干扰**
- 判绿：① 在会话 1 问 3 轮 → ② 点"新对话" → 输入框清空、消息区清空 →
  ③ 问一个完全不同的问题（此时上下文里不该有会话 1 的内容）→
  ④ 点回会话 1，它的 3 轮问答原样还在。
- 怎么验：切换过程中看 Network 有没有多余请求；第 ③ 步的答案里不能出现会话 1 的内容。
- 不通过意味着：多轮上下文串会话 —— 比报错更糟，因为它只是"答案偶尔沾点别的话题"。
