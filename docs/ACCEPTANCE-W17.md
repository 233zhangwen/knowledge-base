> 状态：**已完成**（2026-11-01）。2 项决策已拍板；实施中 5 处偏差见第 10.1 节
> 前置：W16 完成（`821d815`）。单测 110 绿，52/52 答案正确，**token +107% 未达标**
> 日期：2026-11-01

## 0. 为什么这个 W 值得单独做

W16 留下一个没通过的判据：input token 从 3629 涨到 7535（**+107%**，上限是 +60%）。当时把它归因为「模型多检索了几次」，并且用 `AGENT_MAX_RETRIEVALS=3` 压住了一部分。

但根因不是检索次数。**是模型在拿到证据的那一刻，没有信息判断这份证据属于哪一版。**

看 m02 的实际过程：

```
问：成都研发中心员工的婚假是多少天？
第 1 次检索 → 命中 F#5「婚假…按国家规定与母公司标准执行」
               ↑ 这是一个指针，不含数字
第 2 次检索 → 命中 E#1「婚假 10 天」（2024 版）和 C#2「婚假 12 天」（2026 版）
               ↑ 两份都在手里，正文 95% 相同，唯一差别在最后一个块里那句"废止"
第 3 次检索 → 才追到 C#8「此前发布的《员工手册（2024 版）》同时废止」
```

**答案从来不是"检索不到"，而是"分不清"。** 而分不清的原因是：块的正文里没有版本信号，信号在另一个块里。

这正好接上 W15 的结论——当时写着「rerank 治不了符号消歧（这个数字属于哪一版），那是元数据问题」。W17 就是去解那个被推迟的问题。

## 1. 先看清这次要打的是什么

### 1.1 元数据其实存在，只是位置错了

我把库里 6 篇文档的真实情况查了一遍：

| 文档 | 头部有「生效日期：」 | 文末有「…同时废止」 | 备注 |
|---|---|---|---|
| C 星海科技员工手册（2026 完整版） | **无** | ✅ 第 3706 字 | 它是 W2 造的，没有公文头 |
| E 员工手册（2024 版） | ✅ 第 45 字 | ✅ 第 3475 字 | |
| F 成都研发中心管理制度 | ✅ 第 45 字 | **无** | 新制度，不废止任何东西 |
| G 差旅与费用管理办法 | ✅ 第 43 字 | ✅ 第 2493 字 | |
| H 信息安全与数据合规管理办法 | ✅ 第 46 字 | ✅ 第 2097 字 | |
| I 实习与试用期管理办法 | ✅ 第 43 字 | ✅ 第 2577 字 | |

两条结论，都会直接影响实现：

1. **不能只做公文头路径**。C 是最关键的文档（它才是现行版），而它恰恰没有文件头。5/6 有文件头这个比例会骗人。
2. **元数据是"文档级"的，但检索返回的是"块级"的**。C#2 里没有生效日期，C#8 里有——而 C#2 才是命中婚假问题的那一块。**块级检索 + 文档级元数据，中间缺一层传递**。W17 要补的就是这一层。

### 1.2 现在围栏头里已经有标题了，为什么还不够

`fenceChunk` 现在输出：

```
<<<DOC [1] 《E-星海科技员工手册(2024版).md》第 3 段>>>
```

标题里明明白白写着「2024 版」，模型还是照抄了它的数字。三个原因：

- **「2024 版」不等于「已废止」**。模型看到 2024，完全可能认为那是"2024 年修订的最新版"——而 C 标题里没有年份，反而更像旧的。**这是在信息不足时做出的合理推断，不是疏忽。**
- **文件名前缀（`E-`）是测试脚手架的痕迹**，对模型是噪声，占用了注意力。
- **`.md` 后缀**也是噪声。

要让模型不误判，必须给它**它自己推不出来的那个事实**：谁废止了谁。

### 1.3 所以本周的真实形状

不是"加个字段"，是两件事：

- **A 组（抽取）**：从正文把「生效日期」和「废止关系」抽成结构化字段。**必须能处理两种文档形态**（有/无公文头），并且对抽错有明确态度。
- **B 组（注入）**：把文档级元数据下沉到每个块上，**不新增行、不新增调用**——直接延长围栏头那一行。这是 token 成本最低的形态（围栏头模型必读，且已经存在）。

外加 **C 组（对齐）**：C 说它废止了《员工手册（2024 版）》，库里的标题是 `E-星海科技员工手册(2024版).md`。**两者不是字符串相等**（全角/半角括号、书名号、文件名前缀、无空格 vs 有空格）。这是实体对齐，不是正则。

## 2. A 组：元数据抽取（纯函数，离线可测）

### A1 抽什么

```
effectiveFrom : Date | null      生效日期
supersedes    : string[]         本文件废止的文件名（原始写法，未对齐）
status        : 'active' | 'superseded' | 'unknown'   ← 由 C 组对齐后推导，不直接抽
```

`status` 不抽，是推出来的。这个区分很重要：抽出来的是事实（日期、废止声明），推出来的是关系（谁取代谁）。混在一起会让"对齐失败"和"没写废止声明"变成同一种状态。

### A2 三条抽取路径（优先级从高到低）

| 路径 | 形态 | 覆盖 |
|---|---|---|
| ① 公文头 | `> 生效日期：2024 年 1 月 1 日` | E/F/G/H/I（C 没有） |
| ② 正文句 | `本手册自 2024 年 1 月 1 日起施行` | 全部 6 篇 |
| ③ 标题年份 | `# 星海科技员工手册（2024 版）` | 兜底，**只记版本标签不记日期** |

**①优先于②，但两者不一致时必须留痕**——公文头写 1 月 1 日、正文写 2 月 1 日，这是真实的公文错误，不能静默取一个。

### A3 硬要求

- **零依赖纯函数**（与 `untrusted.ts`、`context-budget.ts` 同一条纪律）：单测不 mock，脚本能直接 import 生产代码
- **日期必须能解析成 Date**，不只是存字符串——「2026 年 3 月 1 日」和「2026-03-01」要能比大小
- **不猜测**：只有明确写出「废止」「失效」「取代」才算废止声明。没写 = 不知道，不是"没有废止"

### A4 抽取的已知陷阱（写进单测）

1. 「12 月 31 日自动失效」——这是**额度到期**，不是文档废止。必须排除（E#40 就有这句）
2. 「本手册自 2024 年 1 月 1 日起施行，此前发布的《员工手册（2021 版）》同时废止」——**一句话里两个日期 + 一个废止目标**，要正确配对
3. 中文数字日期（「二〇二六年」）——公文中真实存在，按是否支持决定，**若不做必须显式声明不支持**
4. F 的「母公司《员工手册》与本制度不一致的，在成都研发中心范围内以本制度为准」——**这是适用范围声明，不是废止声明**，不能误判为推动 E 废止

## 3. B 组：注入（并入围栏头，不新增行）

### B1 目标形态

```
现在：<<<DOC [1] 《E-星海科技员工手册(2024版).md》第 3 段>>>
之后：<<<DOC [1] 《星海科技员工手册（2024 版）》第 3 段 · 2024-01-01 生效 · 已被《星海科技员工手册（2026 完整版）》废止>>>
```

三个变化：

1. **标题用文档内的 H1，不用文件名** —— 去掉 `E-` 前缀和 `.md`，那是对模型无意义的脚手架痕迹
2. **加生效日期** —— 模型能直接比大小
3. **加废止关系** —— 补上模型推不出来的那个事实

### B2 为什么并进围栏头而不是新增一行

| 方案 | token 增量 | 可靠性 |
|---|---|---|
| **并入围栏头（选）** | ~14 token/块（只是变长） | 围栏头是块的边界标记，模型必读 |
| 新增一行 `【元数据】` | ~22 token/块 | 多一行噪音，且和正文混在一起 |
| 只在首次遇到该文档时说明一次 | ~5 token | 省，但长上下文里模型会"忘"，且块顺序变化时难保证 |

按 52 题 × 2.4 次检索 × 5 块估算：并入围栏头约 +17k token 总量 ≈ **+4%**；新增一行约 +27k ≈ +7%。差别不大，但并入围栏头更省且更可靠，没有理由选差的。

### B3 检索返回类型要加字段

`RetrievedChunk` 加 `effectiveFrom` / `status` / `supersededByTitle`。**注意**：`retrieve()` 里那段 SQL 是手写的（pgvector，Prisma 读不了 embedding 字段），JOIN 要跟着改。

⚠️ **W16 刚踩过的坑**：任何绕过 `retrieve()` 手抄 SQL 的地方都是漂移源。这次改 SQL 之后要确认 `eval-rerank.mts` 那份 SQL 也同步——它有自己的一份。

## 4. C 组：废止关系的实体对齐（本周最难点）

### C1 问题

| 来源 | 写法 |
|---|---|
| C 文档正文 | `此前发布的《员工手册（2024 版）》同时废止` |
| 库里的标题（文件名） | `E-星海科技员工手册(2024版).md` |
| 库里的 H1（文档内标题） | `星海科技员工手册（2024 版）` |

三者都不相等。全角/半角括号、书名号、`E-` 前缀、`.md` 后缀、空格差异。

**用 H1 对齐比用文件名对齐干净得多**——这也是 B1 里"标题用 H1"的第二个理由：对齐和展示共用同一个来源，不会出现"对齐用的是 A、显示的是 B"。

### C2 匹配策略

规范化 → 精确匹配 → 失败则覆盖率匹配 → 仍失败则**不标**。

- 规范化：去书名号/文件名前缀/扩展名，全角转半角，去空白
- 覆盖率：规范化后 `A` 的字符有多少比例出现在 `B` 里（双向取小）
- **阈值宁可高不可低**：错标一份现行文档为"已废止"，比不标危险得多——不标只是回到今天的状态，错标会主动误导

### C3 对齐失败的三种情况必须分开

| 情况 | 含义 | 处理 |
|---|---|---|
| 声明了但库里没有那份文档 | 引用外部文件（如《员工手册（2021 版）》不在库） | 忽略，正常 |
| 声明了、库里有、但匹配不上 | 我的对齐算法不够好 | **记录**（`/admin` 可见），这是要修的 |
| 没声明 | 不知道 | 不标 |

第三种和第二种外观相同（都标不出来），但对运维的意义完全相反。**不能混。**

## 5. D 组：评测（判据先写死）

### D1 对照组设计

W17 的核心论点是「元数据注入能替代一次检索」。要验证它，必须做**关掉指路提示**的对照——否则省下的检索可能只是 prompt 规则没触发，跟元数据无关。

四组：

| 组 | pointerHints | 元数据 | 用途 |
|---|---|---|---|
| **A0** | 关 | 关 | 纯基线（≈ W16 起点，但无 prompt 规则） |
| **A1** | 关 | **开** | ★ 核心：元数据单独能不能救 m02 |
| **A2** | 开 | 关 | W16 现状（2.42 次/问，7535 token） |
| **A3** | 开 | 开 | 两者共存，是不是冗余/叠加 |

`pointerHints` 需要能通过环境变量关掉（`AGENT_POINTER_HINT=off`），这是 A/B 的前提。

### D2 判据

| 编号 | 判据 | 门槛 |
|---|---|---|
| D2-1 | 答案层不退化 | ≥ 52/52（一条都不许掉） |
| D2-2 | **A1 组 m02 答对** | 必须 ✓ 否则元数据没起作用 |
| D2-3 | A3 组平均检索次数 | ≤ 2.42（W16 值） |
| D2-4 | A3 组 input token | **≤ 5800/问**（W16 的 7535 × 0.77，即把 +107% 压到 +60% 以内） |
| D2-5 | 抽取准确率 | 6 篇文档的生效日期，人工核对 **6/6 全对** |
| D2-6 | 对齐不误判 | 无任何现行文档被标成「已废止」 |

> D2-4 是本周能不能算成功的唯一硬指标。W16 没达标，这周必须补上，否则连续两个 W 交不出成本账。

### D3 单测清单（D 组外的确定性验证）

- 三条抽取路径各自的命中与不命中
- 头部与正文日期不一致时要留痕
- 「12 月 31 日自动失效」不被当成废止
- 一句话里两个日期 + 一个废止目标要正确配对
- F 的「以本制度为准」不被当成废止声明
- 规范化：全角括号 / 书名号 / 前缀 / 后缀 / 空格
- 覆盖率阈值边界（刚好过、刚好不过）
- 对齐失败的三种情况分别返回不同状态

## 8. 待决事项

### 决策 1：已废止的文档，除了标注之外要不要影响检索？→ **① 只标注（已选）**

- **① 只标注，不动排序（已选）** —— 排序是检索的事，元数据是理解的事，两件事不该耦合。而且"用户问 2024 年的规定"是合法需求，过滤掉就答不了。风险最低，也最符合本项目"先给模型事实、让它自己判断"的一贯做法
- ② 标注 + 检索时给已废止文档降权 —— 看起来更聪明，但降权系数没有依据可循，且会让 W15 的 rerank 评测基线作废（排序变了）
- ③ 标注 + 默认过滤（无现行版时才回退）—— 效果最"正确"，但一旦对齐标错，现行文档被过滤 = 直接答不出。**把对齐算法的可靠性绑在检索可用性上，这个耦合太危险**

> 落地约束：`retrieve()` 的排序表达式**一个字符都不许改**。这不是"这次不改"，
> 是写进代码注释的纪律——元数据只出现在 `RetrievedChunk` 的字段里，不进 `order by`。

### 决策 2：废止关系怎么建立？→ **① 自动抽取 + 自动对齐（已选）**

- **① 自动抽取 + 自动对齐，失败就只留痕不标（已选）** —— 零人工，宁可漏标不可错标。漏标的后果是回到今天的状态（模型自己追），错标的后果是主动误导
- ② 自动抽取 + `/admin` 人工确认 —— 准确率最高，但要加一个待确认列表 UI，本周做不完
- ③ 只做文档级提示，不建立废止关系（"库中存在多份同名文档，注意核对生效日期"）—— 最保守，但等于把对齐的活又丢回给模型，D2-2 大概率过不了

> 落地约束：「失败只留痕」要求失败原因**可查**。对齐失败写 `ErrorLog`
> （`event=docmeta.align_failed`），/admin 已有的错误表直接显示/用它，不新造表。

## 10. 实施记录

### 10.1 与 spec 的偏差（逐条说明）

| # | spec 里写的 | 实际做的 | 为什么 |
|---|---|---|---|
| 1 | `effectiveFrom` 用 `DateTime` | **改成 `String`（`YYYY-MM-DD`）** | Prisma 的 DateTime 映射成 `TIMESTAMP(3)`（不带时区），写入按 UTC 字面值存、读回按本地 +08 解释 —— 2026-01-01 存进去读出来是 2025-12-31。**根因不是时区没处理对，是类型选错了**：生效日期没有时分秒，也就没有时区 |
| 2 | A2 的路径③「标题年份兜底」 | **没做** | 能抽到年份的文档都能抽到日期；年份单独记没有消费方。做了就是死代码，lint 也会报 unused |
| 3 | 决策②只说「失败留痕」 | **区分了三种失败** | `ambiguous`/`too-short` 落 ErrorLog（那是我的算法不够好）；`not-found` 只打印（那是引用了库外文件，正常）。混在一起报会把真异常淹掉 |

### 10.4 顺带查出来的问题（不在 spec 范围内，但都是真的）

**① 两处 `expectChunks` 指错了块。**

| 用例 | 问的是 | 原来标的块 | 实际答案所在 |
|---|---|---|---|
| v03 | 辞职提前多久 | C#8（《离职交接单》交接流程） | **C#7**（「应提前 30 天以书面形式通知公司」） |
| c20 | 未休年假最多折算几天 | C#7（差旅与外派 / 离职通知期） | **C#8**（「最多折算 10 天」） |

两个都是自洽的错：`--check` 校验「snippet 与块首匹配」，两块的首行都对得上，所以放行。
但它校验不了「这块回答得了这个问题」—— 这两件事被混为一谈了。

新增 `npm run check:cases` 补这一环：取 `expectChunks` 的块正文，看里面有没有
`answerMustContain` 的关键词。**它给的是可疑清单，不是错误清单** —— 跨块推导（c19 求和）、
多跳第二跳（m02）、同义表达（m05 的「不得接触」对判据「不可以」）都会正常出现在里面，
需要人看一眼。跑完全库命中 3 条，全部是上述正常情况。

**② `scripts/lib/env.mjs` 的存在理由。**

之前 4 个脚本各抄一份 `loadEnv`，其中我新抄的那份漏了「行内注释」分支，
于是 `DATABASE_URL=... # 应用运行时用` 读进来带上了注释尾巴，连接串解析成
`host: 'base'`，报 P1001「连不上库」—— 看起来像网络问题，实际是 20 行解析器少一个分支。
统一成一份之后这类漂移不会再发生。

### 10.5 已知问题（不改，说明理由）

**C 文档的 H1 带着「W5 专用」**（`星海科技员工手册（2026 完整版 · W5 专用）`）。
那是 W2 造测试文档时留下的脚手架标识，现在会一路显示到围栏头里，作品集演示时扎眼。

不修的理由：改 H1 就得改 `content`，改了 `content` 就要重切片，重切片之后
52 条 case 的 `snippet` 指纹全部失效。**为了一个显示问题让整个评测基线作废，不划算。**
正确的修法是换一份干净的文档重新上传，那是独立的一件事（W18 候选）。

`docTitle` 是独立字段，理论上可以单独改，但下次 `backfill:meta` 会从 `content` 重新抽、
把手工改动覆盖掉 —— 与其加一套「人工覆盖」机制，不如把文档本体修好。
