# W3 验收 spec：切片 + 嵌入

> 范围：`chunk.ts`（切片）/ `embedding.ts`（向量化）/ `index-document.ts`（编排）+ 接进上传链路。
> 本轮补录：F 组（规模与限流）—— 原 spec 漏掉了"大文档怎么办"这一整档，那是同步 await 方案下必然会发生的事。
> 关键常量：`EMBED_BATCH_SIZE = 16`（实测 32 条短文本通过，留一倍余量）、`MAX_CHUNKS_PER_DOCUMENT = 200`。
> 原则：**每条标准都必须能被一个具体操作证伪**。写不出具体操作的（"切片质量良好"之类）不算标准。
> 用法：逐条打勾，任何一条不绿就先修代码再往下走 —— W4 的检索建立在这层之上，这层有洞，W4 的怪结果会无从下手。

## A. 切片（不依赖 UI，用脚本直接跑 `splitText`）

**A1 块数与长度**
- 判绿：输入 1200 字 3 段中文 →
  ① 每块长度落在 `[250, 580]`（最后一块允许更短）；
  ② **不钉死块数**——只要求"没有无故碎片"：任意相邻两块满足 `len(a) + len(b) - 80 > 500`（能合并却没合并的，就是碎片）；
  ③ 块数 ≥ 2。
- 怎么验：`node -e` 调 `splitText`，打印每块 `length` 并跑一遍 ② 的断言。
- 为什么改成这样：原写法断言"必须 3 块"，那是在**冻结实现**而不是防退化——三段是 200/200/800 字时正确实现会切出 4 块，代码没错验收却红。判据要落在"粒度受控"这个意图上，不是落在某个数字上。

**A2 重叠真的生效**
- 判绿：`chunks[0].slice(-80) === chunks[1].slice(0, 80)`（严格相等）。
- 怎么验：打印这两段对比。
- 不通过意味着：overlap 参数没参与拼装，跨块的句子会在两边都残缺 —— 检索时谁都匹配不上。

**A3 不丢字（最重要的一条）**
- 判绿：把各块按"去掉与前一块重叠的 80 字"重新拼起来，结果与输入**逐字符相等**。
- 怎么验：脚本里 `rebuilt === input` 断言。
- 不通过意味着：切片吞内容。这类 bug 不会报错，只会让答案"少了点东西"，到 W6 评测才会被发现，那时已经无从定位。

**A4 空输入与极短输入**
- 判绿：`''` → 抛出带中文原因的错误（由上层转成 failed）；少于一个块长的短文本（如 5 个字）→ 输出 1 块，不输出 0 块。
- 怎么验：两种输入各跑一次。
- 不通过意味着：空文档会被写成"已就绪但 0 切片"，用户在 W4 问它时永远检索不到东西，还以为模型坏了。

## B. 嵌入与入库

**B1 维度是 1024（查库，UI 上看不出来）**
- 判绿：`select vector_dims(embedding) from "Chunk" limit 1;` → `1024`。
- 怎么验：psql 连 Neon（用 DIRECT_URL）或 Prisma Studio 的 raw 查询。
- 不通过意味着：模型和建表维度不一致。已由 `verify-embedding.mjs` 前置拦截，这里再确认一次"写进去的"而不是"接口返回的"。

**B2 UI 上的切片数 = 数据库里的行数**
- 判绿：文档列表显示"N 个切片"，且 `select count(*) from "Chunk" where "documentId" = '<id>';` 也等于 N。
- 怎么验：两边对照。
- 不通过意味着：中间有写入失败但被吞掉了（典型：批量插入时部分失败没抛）。

**B3 向量不是空的**
- 判绿（两步，都要）：
  ① `select count(*) from "Chunk" where embedding is null;` → `0`；
  ② 先查版本 `select extversion from pg_extension where extname='vector';`
     - **≥ 0.7.0**：`select min(vector_norm(embedding)) from "Chunk";` → 结果 > 0
     - **< 0.7.0**：`select count(*) from "Chunk" where embedding::text !~ '[1-9]';` → `0`
       （向量的文本形式里一个非零数字都没有，就等价于全 0）
- 为什么改成这样：原写法在版本不支持时兜底成"打印出来肉眼确认"，那不是标准，是"你自己想办法看看"。现在两种版本都有确定的动作和确定的结果。

**B4 冒烟：向量真的能用**
- 判绿：取原文里的一句话做 embedding，用余弦距离查 top 1，返回的 chunk 属于**同一篇文档**。
- 怎么验：一段 raw SQL（`order by embedding <=> $1::vector limit 1`）。
- 不通过意味着：向量写反了顺序 / 维度错位 / 距离运算符用错。现在查比 W4 查便宜得多 —— W4 出问题时你会先怀疑 Prompt。

## C. 失败路径

**C1 索引失败要看得见**
- 判绿：把 `.env.local` 里的 `EMBED_API_KEY` 改成一个错的值，重启 dev，上传一个文档 → 状态变成 **failed**，列表红字写明原因（不是"已就绪"、也不是"点了没反应"）。
- 怎么验：改 key → 重启 → 上传 → 看列表。验完把 key 改回来。
- 不通过意味着：静默失败。这是本项目反复强调的头号敌人。

**C2 失败不留半成品**
- 判绿：上一条那次失败之后，`select count(*) from "Chunk" where "documentId" = '<id>';` → `0`。
- 怎么验：同 B2 的 SQL。
- 不通过意味着：留下一批没有向量的 chunk，W4 检索会把它们当有效内容捞出来（向量为 null 时排序行为不可预期）。

## F. 规模与限流（补：原 spec 完全没覆盖这一档）

**F1 大文档有护栏，不会把函数拖到超时**
- 判绿：上传一篇能切出 **超过 200 块**的文档 → 文档状态变 **failed**，红字写明「文档过长（N 块，上限 200），请拆分后上传」，**不是**页面转圈直到平台 504、也不是写一半。
- 怎么验：造一个大 txt（>10 万字）上传，看状态与提示。
- 为什么必须有这条：W3 定案是**同步 await**，而 W2 的 4MB 上限挡不住它——中文 UTF-8 一个字 3 字节，4MB ≈ 140 万字 ≈ 2800 块，按 16 条一批要发 175 次请求，必然撞 Vercel 函数超时。**"文件不大"和"切片不多"是两件事**，必须单独设限。
- ⚠️ 本地 dev 没有函数超时，这条护栏在本地看不出效果 —— **W7 部署后要复验一次**。

**F2 网络/限流失败会退避重试，而不是一次就判死**
- 判绿：把 `.env.local` 里的 `EMBED_BASE_URL` 临时改成一个不可达的地址，重启 dev，上传文档 → dev 终端日志里能数出**多次重试**（不是只请求一次），最终状态 failed 且提示含失败原因。验完改回来。
- 怎么验：数日志里的重试行 + 看总耗时是否 ≈ 各次退避间隔之和。
- 不通过意味着：一次抖动就判失败。429 限流在批量调用时是常态，没有退避重试等于把可用性交给运气。

## D. 幂等

**D1 重复索引不重复、不报错**
- 判绿：对同一文档连续触发两次索引 →
  ① 控制台**没有** P2002 唯一约束错误；
  ② `select count(*), count(distinct "chunkIndex") from "Chunk" where "documentId" = '<id>';` 两列相等（无重复下标）；
  ③ 最终条数等于**最后一次**切片的产出（不是"与第一次相同"）。
- 怎么验：调两次 `indexDocument`，前后各 count 一次。
- 为什么改成这样：原写法用"两次条数相同"判幂等，但 W6 换切片策略后重新索引，条数**合法地**变化——正确的行为会被判成失败。幂等要验的是"不重复、不残留"，不是"数量不变"。

## E. 回归

**E1 W2 的六条全绿**
- 判绿：md/txt 就绪、真 PDF 就绪、小假 PDF 失败可见、删文档清存储、删知识库连带清理、20MB 文件客户端拦截 —— 六条重跑一遍。
- 不通过意味着：W3 改了上传链路（`uploadDocument`）碰坏了 W2。这是最容易发生的事 —— 上传 Action 里加了索引调用，等于动了 W2 的心脏。
