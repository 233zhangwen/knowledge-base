# W11 验收 spec · Agent 化收尾：退役 / 打磨 / 文档对齐

> 本 spec 由 p 老师执笔（2026-10-29）。范围裁定基于三项侦察事实（见背景）。
> 修订记录在文末。

## 背景

W10 完成了 Agent 化主链路（方案 B：新旧端点并存）。本周把并存期结束后的账清掉：

- 侦察事实 ①：`loadContext` 已有历史窗口（`HISTORY_TURNS*2`，倒序取再反转），
  W10 C2 记录的成本差距（in ≈2.2x）来自多步循环的消息重发——工具调用的固有成本，
  国内 provider 无 prompt cache 可靠支持。**成本优化降级为只记录，不施工。**
- 侦察事实 ②：旧端点 `/chat` 已无引用方（ChatPanel 走 `/chat-agent`，脚本不依赖 HTTP）。
- 侦察事实 ③：README 的 Out of Scope 仍列着"Agent 式 query 改写与多轮工具调用"，
  功能清单与架构图也还是"必检索"叙事——文档与现实已脱节。

## 本周范围

1. **A 组 · 旧端点退役**：删除 `/api/kb/[id]/chat/route.ts` 及 `llm.ts` 中仅被它使用的导出
   （逐个核实引用后再删，`llm.ts` 若仍被 agent 路径或脚本共用则只删死代码）；
   协议 v1 的编码/解码函数**保留**（verify-stream-protocol.mts 仍测它，且是协议演进的活文档）。
2. **B 组 · E2 检索状态提示**：ChatPanel 消费 `cursor.toolQuestion`——
   流式占位气泡在收到 tool 事件、尚无文本时显示"正在检索：xxx"；
   文本开始后提示消失。纯展示层，不碰协议与数据。
3. **C 组 · 数据污染核查（先核查后决策）**：搜 B1 专用文档源文件中的 "TOP_K" / "W5 spec"；
   命中则如实记录污染范围，**清洗方案由用户拍板**（见"待决事项"）。
4. **D 组 · 文档对齐**：README——功能清单加 Agent 化（模型决定何时检索、查询改写、
   多步工具调用、错误恢复）；Out of Scope 删"Agent 式…"；架构图补 tool 循环与协议 v2 哨兵；
   新增 ADR-9（协议边界显式声明：哨兵优于试探）与"已知限制"一节
   （数据质量击穿答案层的实测案例 + Agent 知识类成本对照，均引自 W10 观测记录）。
5. **E 组 · 回归**：`tsc` 0 错误；verify-stream-protocol 全过；
   eval-agent 全量重跑（退役后），recall@3 ≥ 0.90、答案层退化 ≤1 条。

## 验收标准

### A 组 · 退役

- **A1**：`grep -r "chat/route\|'/chat'\|/chat\`" src scripts` 无业务引用残留；
- **A2**：`npx tsc --noEmit` 0 错误（删除未破坏类型）；
- **A3**：`node scripts/verify-stream-protocol.mts` 全过（v1 用例仍在，证明协议代码未误删）；
- **A4**：网页问答、历史、删除会话手点一轮无异常（新端点路径未受牵连）。

### B 组 · E2 检索状态提示

- **B1**：问知识库问题 → 占位气泡先出现"正在检索：…（模型改写的问句）"，文本到达后消失；
- **B2**：问"你好" → 不出现提示（无 tool 事件）；
- **B3**：D3 式工具失败 → 提示出现后随错误/答案消失，不残留；
- **B4**：提示是流式更新的一部分（不阻塞、不替换答案渲染）。

### C 组 · 数据污染

- **C1**：对 B1 专用文档源文件 grep "TOP_K"、"W5 spec"、"带宽词汇量"（或当时对话特征词），
  结果写进观测记录（命中/不命中都是结论）；
- **C2**：若命中，量化污染：污染在源文件哪些段落、对应几个 chunk、是否波及 eval 期望块
  （对 cases.json 的 expectChunks 做一次核对）。

### D 组 · 文档对齐

- **D1**：README 功能清单含 Agent 化描述；Out of Scope 不再含"Agent 式…"；
- **D2**：架构图（mermaid）含 retrieve 工具循环与 v2 哨兵时序；
- **D3**：ADR-9 与"已知限制"落地；W10 的评测数字引用自 ACCEPTANCE-W10 观测记录，不新造。

### E 组 · 回归

- **E1**：eval-agent 25 条全跑，指标达门槛（recall@3 ≥ 0.90、答案层退化 ≤1）；
- **E2**：若 C 组做了清洗重建 → 期望块可能有变，**先对齐 cases.json 再跑**，
  且新旧指标都记录（换基线要留痕）。

## 反证（用户执行）

- **R1**：curl 已删除的旧端点 `/api/kb/<id>/chat` → 预期 404（删干净了）；
- **R2**：问一句闲聊 → 页面**不**出现"正在检索"提示（B2 的反方向）；
- **R3**：如果 C 组选择清洗重建：用被污染段落附近的问题重问，确认引用不再含 spec 文本。

## 待决事项（需要用户拍板，spec 不代答）

**C 组若证实源文件污染，两条路**：

| | 内容 | 代价 | 收益 |
|---|---|---|---|
| ① 记录不清洗 | 污染现状写进 README 已知限制 | 零 | 评测基线不动；诚实案例保留 |
| ② 清洗重建 | 修源文件 → 重传重建索引 → 核对/更新 cases.json → 重跑双评测 | 半天；基线换轨要留痕 | 知识库恢复干净；顺带演练"索引重建流程" |

倾向：**① 先记录，② 留给"索引重建流程"单独演练时一起做**——避免本周同时动
文档、代码、数据三个面。

## 自我挑漏洞（写 spec 时自己先戳的）

1. **删 `/chat` 会不会破坏生产**：Netlify 自动部署新 commit，删端点的瞬间
   若有人开着旧版前端页面（缓存的旧 JS 指向 /chat）会 404——个人作品集无真实用户，
   接受；但 commit message 里写明这个窗口。
2. **v1 协议代码保留的边界模糊**：`llm.ts` 若被 agent 共用就不能整文件删；
   逐 export 查引用，宁可少删不误删（A2 tsc 兜底）。
3. **E2 提示与 288px/滚动跟随的相互作用**：提示改变占位气泡高度，
   滚动跟随逻辑（stickToBottom）必须仍生效——B4 的隐藏判据。
4. **C 组清洗的连锁反应被低估**：重建索引会改 chunk id，expectChunks 的
   snippet 指纹可能失配 → eval 全红是"数据变了"不是"代码坏了"。
   这是倾向方案 ① 的核心理由。
5. **README 更新与现实的再脱节**：文档对齐当天如果又有行为变化就白写——
   D 组放在 A/B 组落地之后执行，作为本周最后一个 commit。
