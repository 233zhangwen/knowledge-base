# W4 验收 spec（RAG 问答：检索 + 生成 + 溯源）

> 范围：答案的核心链路 —— 提问 → 检索（查哪些片段）→ 生成（模型怎么回答）→ 溯源（引用怎么挂）。
> 每条三段式：**判绿标准 → 怎么验 → 不通过意味着什么**。
> 第三段最关键：它说明这条标准在防什么。不知道在防什么的标准，验收时会退化成机械打勾。

---

## 先说三个技术决策（数字怎么来的，你照着能自己推一遍）

**① top-K = 5**
一块约 500 字，5 块 ≈ 2500 字 ≈ 2500~4000 token，加提问和回答也远在 DeepSeek 上下文窗口内。
所以限制我们的**不是窗口大小，是注意力稀释**：塞 20 个片段进去，真正有用的那条会被淹没，
模型反而更容易忽略它。取多了变差、取少了漏召回，5 是常见折中。
→ 想验证这个判断：临时改成 20，问同一个问题，看答案是不是开始含糊。

**② 不用「绝对相似度阈值」硬拦 —— 这是我从你的实测数据里得出的结论**
实测（见下）显示：**瞎问一个泛泛的问题也能拿到 0.47~0.50 的相似度**，
而同一文档里相邻块之间是 0.74~0.81。也就是说：
- 设 0.5 当阈值 → 会误杀真正相关的内容；
- 设 0.8 → 只有完全一样的段落才能过。
**绝对阈值不可靠**，因为不同文档、不同提问方式的分数分布根本不在一个尺度上。

替代方案（MVP 就这么做）：**不靠分数裁断，靠 Prompt 约束模型**。
在 system prompt 里写死："只能依据下列片段回答；片段无法回答时，直接说文档里没有相关内容，不许用你自己的知识补全。"
同时在日志里打印 top1 的 sim 值用于**观察**（W6 调策略时的依据），但不拿它做开关。

**③ MVP 是单轮**：不存历史、不带上下文。理由写在本文末尾「Out of Scope」。

## A. 检索

### A1 跨知识库隔离 —— 本份 spec 里最严重的一条

- 判绿：知识库 A 装「A 主题」文档、B 装「B 主题」文档。
  在 `/kb/{A}` 页面问 B 的问题：出现的**所有引用都属于 A 的文档**，`documentId` 集合与 A 完全重合。
  把 URL 换成 `/kb/{B}` 问同一个问题，结果必须翻转。
- 怎么验：
  1. 两个库各放一份主题鲜明的文档；
  2. 先在 A 里问 B 的问题，看答案下面挂的引用属于哪个库；
  3. 更硬的证据：`node scripts/db-query.mjs` 或直接 SQL
     `select "documentId", "chunkIndex" from "Chunk" ...`，把命中的 id 和 A 的文档 id 列表对照。
- 不通过意味着：检索 SQL 漏了 `kbId` 过滤（典型写法：`ORDER BY embedding <=> $1 LIMIT 5` 而没 `WHERE d."kbId" = $2`）。
  这是**静默事故**：用户看到一堆看起来挺相关的引用，完全不会想到那是隔壁知识库的内容。
  这是全项目最该守住的一条 —— 数据越界比功能坏了严重一个量级。

### A2 检索能命中真正相关的片段

- 判绿：准备 3 个**针对文档具体细节**的问题（人名、术语、某个步骤），每个问题的 top1 必须是包含那个细节的片段。
  3 个里至少 3 个命中（允许 2 个算黄灯，需要说明原因）。
- 怎么验：`node scripts/verify-retrieval.mjs "具体的细节问题"`，看 #1 片段里有没有那个 keyword。
  页面上的等价验证：提问后点开引用，确认文本内容对得上。
- 不通过意味着：要么 embedding 质量不行（换模型），要么检索 SQL 的排序方向写反了。
  **注意 `<=>` 是距离，越小越相似** —— 写反了不难 imagine 吗？很容易，而且排序看起来"有结果"。
- ⚠️ 提问方式决定这次能否验出东西：拿你那份「三千字短文」这种**句式雷同的填充文本**问泛泛的问题，
  每块相似度都在 0.47~0.50 挤在一起，测不出区分度。必须问**具体细节**。

### A3 无相关内容时的行为

- 判绿：问一个文档里**完全不存在**的话题（科技文档问"怎么做红烧肉"），
  答案必须明确说"文档里没有相关内容"或明确表示无法作答 —— **不许编、不许用常识补全**。
- 怎么验：口述提问 + 看答案。进阶：准备一个文档里存在、但细节被改过的说法（见 B4），交叉验证。
- 不通过意味着：Prompt 里缺少"不许用外部知识"的约束，或者模型不听话。
  这条挂了，整个 RAG 就没有存在的意义 —— 那还不如直接问 ChatGPT。

### A4 top-K 上限生效

- 判绿：对一个有 9+ 块文档提问，答案下面挂的引用**不超过 5 条**；
  且在某个调试输出里能看到喂给模型的片段数 = 5。
- 怎么验：先看 UI 的引用数量；再在检索函数里临时 `console.log(topK.length)`（或读代码确认取了 5）。
- 不通过意味着：K 写死成别的值，或忘了 limit。片段太多会把答案带偏 —— 这条是 A 组里最容易"看起来正常"的失败。

## B. 生成

### B1 流式输出

- 判绿：提问后**约 1.5 秒内**出现第一个字，之后持续增量渲染（不是全部生成完一次性出现）；
  生成期间输入框禁用，结束后恢复。
- 怎么验：**两条硬证据，有一条即可证明是真流式**
  （肉眼看到打字机效果不算 —— 前端完全可以假装流式：一次性拿完整响应再用 setTimeout 逐字播放）。
  ① dev 终端日志里 `首字 XXXms` 与 `总耗时 YYYms` **差距明显**（如 631ms vs 8000ms）。
     一次性返回的话这两个数必然相等 —— 最省力也最硬的一条。
  ② DevTools → Network → 该请求在答案吐完前一直处于 **pending**，Response 面板内容随时间增长，
     响应头没有 `Content-Length`（即 chunked 传输）。
- ⚠️ **2026-10-24 订正**：本项目的响应是 `text/plain; charset=utf-8`（自定义行协议），
  **不是** SSE 的 `text/event-stream`。原 spec 把 MIME 类型写死成了判据，属于
  "把实现细节钉进验收标准"（W3 的 A1 是同一类错误）—— 照着它会把正确实现判成失败。
  要验的是**"响应分块到达"**，不是"用了哪种 Content-Type"。
- 不通过意味着：退化为一次性返回。用户体感从"马上就有反馈"变成"盯白屏三秒"，
  这是 RAG 应用最直观的体验分水岭。

### B2 引用只来自真正喂给模型的片段（防幻觉引用）

- 判绿：答案里出现的每个引用编号，**必须落在这次检索出来的那 5 条之内**；
  且 UI 上展开的引用文本与数据库里该 chunk 的 `content` **逐字相同**。
- 怎么验：把模型返回的引用编号集合和检索结果的 `chunkIndex` 集合做对照（临时打印两侧即可）；
  再用 `node scripts/db-query.mjs 'select content from "Chunk" where "chunkIndex" = N'` 比对文本。
- 不通过意味着：模型自己编了个引用编号（很常见，尤其是 `[1][2][3]` 这种写法），
  或者前端显示的是**重新查库得到的内容**而不是当时喂进去的内容。后者更隐蔽：
  中间隔了一段时间的话，两者可能已经不一致。

### B3 生成中途 / 之前失败

- 判绿：两种情况都要有明确反馈，**且已进入界面的文字不丢**：
  - 请求就失败（key 错 → 401）：答案区显示红色错误，输入框恢复可用；
  - 流式传输中断（生成到一半断开）：已吐出的文字**保留在原处**，旁边提示"生成中断"，可以重问。
- 怎么验：① 把 `LLM_API_KEY` 改错 → 重启 → 提问；② 生成到一半关掉代理 / 浏览器断网。
- 不通过意味着：用户拿到的半成品答案被一股脑清掉，或者页面卡在"生成中"永远转圈
  （这正是我们在 W2 修过的那类静默失败）。
- 备注：SDK 的 `onError` 和 `onFinish` 要分开处理 —— 中断不等于没输出。

### B4 答案不许掺杂文档以外的常识

- 判绿：在文档里写一个**故意编造的事实**（比如"本公司年假为 10 天"、某个虚构的产品名/价格），
  然后问它 → 答案必须给出文档里那个**编造的值**，而不是模型的常识答案。
- 怎么验：临时造一个 test.md：`"公司规定：所有员工年假为 10 天。"` → 问"年假有几天" →
  必须答 10 天。再问一个文档里**没有**但模型肯定知道的问题（如"水沸点是多少"）→ 必须拒绝作答。
- 不通过意味着：Prompt 约束不够硬，**当文档的正确答案和模型常识冲突时，模型会不自觉地"纠正"文档**。
  这是 RAG 项目最经典、也最难被发现的缺陷 —— 因为大部分时候它"顺便答对了"。

## C. 溯源与 UI

### C1 引用与答案一致

- 判绿：答案里每处具体论断，都能在它引用的那条片段里找到出处。
  抽查方式：随机取一段答案里的陈述 → 打开它引用的片段 → 肉眼能对上。
- 怎么验：抽 3 处论断，每处都能对上算绿；有 1 处对不上算失败（这条不允许"大部分对"）。
- 不通过意味着：用户点开引用就穿帮。**溯源一旦不可信，整个产品的可信度归零** ——
  比答案答错还严重，因为答错是能力问题，假引用是诚信问题。

### C2 点击引用能看到原来的片段

- 判绿：每个引用可点/可展开，展示**该片段的原文**（至少前几百字）+ 所属文档名 + 第几块。
- 怎么验：点开任意引用，和 db-query 查出来的 content 开头比对。
- 不通过意味着：用户没法判断这条引用到底有没有用，溯源等于做了个摆设。

### C3 非 ready 文档的碎片不能被检索

- 判绿：把某个 ready 文档的 status 手工改成 `failed`（或直接删掉它再提问），
  它的片段必须**立刻**不再出现在任何检索结果里。
- 怎么验：SQL 改状态 → 提问 → 看引用里有没有那个文档的 chunk。
- 不通过意味着：检索 SQL 没有关联 Document 且过滤 status。W3 里失败文档可能残留旧 chunks，
  不去过滤的话，"上传失败删除后仍能搜到内容"这种鬼故事就会发生。

## D. 数据隔离

### D1 别人的知识库问不到

- 判绿：数据库里存在**属于别人 userId** 的知识库 + 文档 + chunk（需要造诱饵），
  在我的知识库里问相关内容 → 引用里**完全没有**诱饵文档的 id。
- 怎么验：仿照 W1 的 `verify-isolation.mjs` 思路，用 SQL 插一个假 userId 的知识库和文档
  （可以直接 `node scripts/db-query.mjs "insert ..."` 跑，脚本只禁 DSL 不禁你手动写 SQL），
  然后提问，比对 `documentId`。**反证**：把 kbId 过滤临时去掉，必须能搜到诱饵 ——
  否则说明诱饵压根没插进去，前面的"搜不到"是假绿。
- 不通过意味着：跨用户数据泄漏。**这条比 A1 更严重**，A1 漏了是串自己的库，这条漏了是看别人的东西。

### D2 提问前的归属校验

- 判绿：把自己的 URL `/kb/{别人的id}` 直接敲进地址栏 →
  页面 notFound（这条 W2 已经保证），**并且**在这个页面（即使通过某种方式进去了）提问会返回无权访问。
- 怎么验：拿上面造的诱饵知识库 id 拼 URL 访问。
- 不通过意味着：Server Action / Route Handler 里没有 `requireUserId()`。
  注意 UI 上"看不到入口"**不等于安全**，接口层必须自己校验。

## E. 回归与观测

### E1 W2 / W3 链路未被破坏

- 判绿：上传 → 解析 → 索引 → 列表显示切片数，整条链路仍然正常；
  重建索引按钮仍可用；W2 那 6 条场景重跑一遍。
- 怎么验：传一个新 txt，看变 ready 且切片数 > 0，再跑 `node scripts/db-query.mjs`。
- 不通过意味着：W4 为了提问改了 schema 或 Prisma client 生成，**回归是这次改动的保险丝**。

### E2 每次提问的成本与耗时可观测

- 判绿：dev 终端能看到**每次提问**的一行日志：检索耗时、召回片段数、top1 相似度、
  生成首字延迟、总耗时、（可选）token 用量。
- 怎么验：问一次，看终端。
- 不通过意味着：W6 调优时你没有任何数据支撑 ——
  到那时候再回头加埋点，就得把 W4 的代码重读一遍。**观测要在写功能时顺便做掉，事后补最贵。**

## Out of Scope（W4 明确不做，写给三个月后的自己）

- 多轮对话 / 对话历史持久化 —— **W5**
- 引用文本高亮定位到文档具体位置 —— W5
- Hybrid Search（向量 + 关键词混合检索）—— W6 调优
- Rerank 二次排序：硅基流动的 `BAAI/bge-reranker-v2-m3` 免费，但 W4 先不上，等 W6 有评测集再说
- Agent 改写用户 query —— 计划里明确排除
- 移动端适配、计费配额 —— 全局 Out of Scope
