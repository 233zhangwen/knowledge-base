## 0. 这个 W 要解决的不是「换个文件」

W17 的 spec 最后留了一节「已知问题（不改，说明理由）」：

> C 文档的 H1 带着「W5 专用」（`星海科技员工手册（2026 完整版 · W5 专用）`），
> 现在会一路显示到围栏头里，作品集演示时扎眼。

不修的理由也写了：改 H1 就得改 `content`，改了 `content` 就要重切片，
重切片之后 52 条 case 的 `snippet` 指纹全部失效。**为一个显示问题让整个评测基线作废，不划算。**

这个判断当时是对的。但它把两件更严重的事顺手盖住了：

**① 评测基准文档不在仓库里。**

C 只存在于 Neon 库里。`kb-fixtures/` 下只有 E–I 五篇，C 是 W2 通过网页上传的，
仓库里连一份原文都没有。也就是说：**52 条用例里有 31 条指向一份别人拿不到的文件。**

任何人 clone 这个仓库、建一个新库、跑 `npm run eval:agent`，都会在锁库那一步停下 ——
不是报错，是那 31 条永远查不到文档。一个不能复现的评测集，说服力要打对折。
作品集演示时被问「这 52 条怎么复现」，现在的答案是「我库里有一份你们看不到的文档」。

**② 「重切片会毁掉基线」不是不可抗力，是数据设计问题。**

`expectChunks` 存的是**块索引**，而块索引是切片算法的**派生物**。
文档一动，派生物全废。这不是"文档太脆弱"，是**锚挂错了地方** ——
挂在派生量上，而不是不变量上。

所以本周两件事，缺一不可：

- **A 组**：把 C 收回仓库，并且真的清理干净（不只是改个标题糊过去）
- **B 组**：把「重锚」做成一条可重复的路，而不是再手工改 31 条

只做 A 不做 B，下次再动任何一篇文档，这 31 条还得手工重来一遍 ——
那就等于把同一个坑留给下一周。

| 方案 | 内容 | 代价 |
|---|---|---|
| **① 写 `realign:cases` + 人工复核（已选）** | 按「旧块正文在新文档里的去向」自动算出新索引与新 snippet，打映射表；被切开/多义/零关键词的单独列出人工看 | 多写一个脚本（约 150 行），但以后任何文档变动都能复用 |
| ② 手工重标 31 条 | 逐条读新块改索引改 snippet | 一次性够用，但没有可复现的过程记录，下次重来 |
| ③ 改数据模型（不存块索引） | case 只存唯一正文片段，索引每次现场解析 | 治本，但 `eval.mjs` / `eval-rerank.mts` / `check-case-annotations.mts` 三处判据逻辑都要改，52 条数据要迁移，本周做不完 |

选 ① 而不是 ③，是**范围控制**，不是认为 ③ 不好 —— ③ 的收益记在 §8 的后续候选里。
本周要证明的是"重锚可以机械化"，不是"把评测框架重写一遍"。

## 4. B 组：重锚脚本

### 4.1 锚在哪

**不变量**：正文文字本身（A1 保证它一个字没动）。
**派生量**：块索引、块首 `snippet`（会随切片算法变化）。

所以重锚的语义是：**"旧块里的那段正文，现在落在哪个新块里？"** —— 而不是"索引加几减几"。

### 4.2 算法

```
对每条 case 的每个 expectChunk：
  1. 取旧块的正文区间 [start, end)（旧文档坐标）
  2. 用「正文起点偏移差」把区间映射到新文档坐标
     （C 的正文起点从第 278 字变成第 98 字，差 -180；正文内部相对位置不动）
  3. 在新块序列里找与该区间重叠最多的块 → 候选新索引
  4. 判定：
     - 重叠 ≥ 60%        → 唯一命中，自动改
     - 重叠 < 60%        → 块被切开，进人工清单
     - 找不到            → 进人工清单
  5. 新 snippet = 新块的开头 20 字（**必须是块首**，不能"包含即可"）
```

第 5 步是硬要求：`eval.mjs --check` 用的是 `head.startsWith(snippet)`，
snippet 只要不是块首就会报"标注已过期"。**这个检查是好事** —— 它逼着锚点跟着真实切片走，
而不是写一个随便能在块中间找到的字符串。

### 4.3 输出形态

```
c01  #0 -> #0   ✓ 唯一
c12  #5 -> #4   ✓ 唯一（旧块被切开 62%，优先块取 #4）
c20  #8 -> ?    ⚠ 关键词命中 6 块，需人工
```

默认 `--dry` 只打印，`--write` 才写回 `cases.json`。写回时保留字段顺序与缩进风格。

### 4.4 两道校验（缺一不可）

| 校验 | 查的是 | 命令 |
|---|---|---|
| `eval.mjs --check` | snippet 是否仍是**块首**（结构） | `node scripts/eval.mjs --check` |
| `check:cases` | 块的正文里到底**有没有答案**（语义） | `npm run check:cases` |

W17 已经证过这两个查的不是一回事：v03 / c20 的索引指错了块，`--check` 全部放行。
重锚之后两道都要跑，且 `check:cases` 的可疑条数不能比改前多。

### 9.4 C5 为什么没通过（不修饰）

v04 问「未休年假折算工资的倍数标准」，答案句「未休年假按日均工资的 2 倍折算」在离职结算段。
重切片后该块从 `#8`（378 字）变成 `#7`（460 字），前面多了「辞职提前 30 天」那一段，
**同一句话的余弦相似度从 0.5818 掉到 0.5271**，直接掉出粗排前 10 —— 连 rerank 都没轮到它。

这不是判据问题（答案对就是对，这次是模型如实说"文档中没有"），
也不是模型问题（温度 0、同一份语料、同一套提示）。**是 500 字定长贪心切片的抽签结果变了。**

不修的理由写在这里，也写进了 `eval/baseline-rebuild.md`：
修它只能动切片策略，而切片策略一动，52 条要再重锚一次，
且无法证明"这次是改进"而不是"再抽一次签"。那是独立的一周。

**它反而是本周最值钱的一条数据**：以前"块边界"这件事没人在意，
现在有一个具体反例可以说明——同内容换一次边界，有的题变容易，有的题直接答不出。

### 9.5 顺带查出来的问题

**① c19 的 `expectChunks[0]` 从建库起就指错了块。**

c19 问「年假 + 婚假合计多少天」，两个期望块里第一个指的是**考勤 / 迟到公示**块。
两道校验都放行：`--check` 只验指纹，`check:cases` 只看"有没有任何一个期望块含关键词"。
重锚时按内容改成「年假块 + 婚假块」。

和 W17 查出的 v03 / c20 是同一类错误（标了块，但标错了块），说明**这类错不是偶发，
是"标注时凭印象估块号"的必然产物**。真正能挡住它的只有 `check:cases` 那种语义校验，
而它只能给清单、不能给结论。

**② c16 的判据漏了一种写法。**

模型答「按挽回损失的**百分之五**给予奖励，单笔上限 **20000 元**」，判据写的是 `["5%", "20000"]`。
按 `answer-match.mjs` 里既定的规则（不自动转中文数字，遇到就把两种写法都写进 `answerAnyOf`）修判据。
W16 记过一次同类误判，方向同样是"把对的判成错的"。

**③ `realign-cases.mts` 自己踩了三个坑，都写进注释了。**

- `expectChunks` 里没有 `documentTitle`（它继承自 case 顶层），第一版直接 `continue` 跳过 →
  85 处锚点只报了 32 处，52 条一条没重锚，脚本却一声不响。**静默跳过是这类脚本最贵的 bug。**
- `cases.json` 是 CRLF 且**混排缩进**（c/v/n/s 段 2 空格，m 段 4 空格）→ 按行首缩进切块在 m01 处必然失败。
  改成括号配对（跳过字符串内部）才对缩进免疫。
- 新指纹取块首 24 字，而块首经常**带换行** → 裸塞进 JSON 直接把文件搞成非法 JSON，
  报错还指在别的行。指纹是要放进 JSON 的字符串，必须先 `JSON.stringify` 转义。
