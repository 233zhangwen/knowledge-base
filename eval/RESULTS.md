## B3 确定性验证记录（V12）

```
node scripts/eval.mjs > r1.txt
node scripts/eval.mjs > r2.txt
diff r1.txt r2.txt     → 空
```

第一次尝试时 diff **非空**（c19 的某块相似度 0.593 → 0.594）。结论：
embedding 是远程服务，同一句问题两次返回的向量浮点尾数会差最后几位。
所以判据改成"排序序列 + 三指标一致"，默认输出不打印相似度（`--verbose` 才打）。
**这不是脚本不稳定，是原判据把精度钉错了地方。**

**第二次仍失败（V17）**：改成"比排序序列"之后 diff 又非空了 ——

```
c18 ... top5=[7,6,3,5,4]     ← 跑第一次
c18 ... top5=[7,6,3,4,5]     ← 跑第二次（@1/@3/@5、hit 全部相同）
```

根因：`"chunkIndex" asc` 二级排序只在相似度**完全相等**时才起作用，
而第 4、5 名的真实差（<1e-3）小于远程服务的抖动幅度 → 顺序翻转。
修法：排序键先 `round(…::numeric, 3)` 归并到测量噪声以下，再交给 chunkIndex。
改完连跑**三次** diff 全空、c18 稳定在 `[7,6,3,4,5]`，指标不变。
**教训：确定性要用"承认测量精度"的方式构造，而不是要求被测系统表现得更精确。**

> 这条和 V12 是同一个错误的两层：V12 想在输出里保留多余精度，
> V17 则想靠一个"看起来确定"的二级排序兜住不确定的浮点。
> 两次都说明同一件事 —— **判据的精度不能超过测量的精度。**

## 实现期抓到的五个自身 bug（写下来，避免下次再犯）

1. **V12 浮点尾数**：见上。教训：跨网络服务的"逐字节一致"几乎总是过强判据，
   要问"这一位小数的变化是不是真的说明行为变了"。
2. **V10 同义反复的检查**：`--check` 第一版做"脚本 K vs retrieve.ts K"比对，
   但脚本的 K 本来就从 retrieve.ts 读 —— 把 `TOP_K` 改成 4 反证时**依然全绿**。
   教训：**检查必须有一个独立的参照点**，自己跟自己比是空转。
   现改为在 `--check` 输出里打印 `K=5（来源 …）`，让改参数的人看见。
3. **V14 口径跟着参数一起变**：召回查询原来写 `limit: K`，于是把 `TOP_K` 改成 3
   时召回只剩 3 条、`@5` 退化成 `@3` —— "改前改后"的数字看着能比，
   其实刻度变了，C2 归因失效。**教训：度量口径的主语必须是"测量"，不是"被测对象"。**
   评测想看多深（≥5）与线上用几条（K）是两个独立的量，必须分开。
4. **V15 实验空转（换了层）**：`--with-llm` 把评测深度 5 条全喂给 LLM，
   而线上只喂前 K 条。于是 K=3 那轮，检索层确实变窄了，
   但 LLM 拿到的上下文**一点没变**（还是 5 条）→ 25/25 全绿，
   差一点就写成"TOP_K 调小无影响"。修成 `hits.slice(0, K)` 后立刻现形：24/25。
   **教训：凡是"模拟线上"的评测路径，每一处取数都要问一句"线上这里取几条"。**
   这条比第 3 条更隐蔽 —— 它不报错、数字还好看，只有做反证才会暴露。
5. **V17 二级排序兜不住浮点抖动**：以为 `"chunkIndex" asc` 就解决了并列问题，
   但它只在相似度**完全相等**时生效；实测 c18 第 4/5 名在两次运行间翻转。
   教训见 B3 一节最后一段：**判据的精度不能超过测量的精度。**

| 日期 | 改动项 | 前置（是否 reindex） | @1 前→后 | @3 前→后 | @5 前→后 | 处置 |

### 第 1 次调优：TOP_K 5→3（回滚）

**为什么选它**：`TOP_K` 是唯一"改一行、不用重建索引"的参数。改切片目标必须
对整个文档 reindex，会让 25 条的 `chunkIndex` 全部漂移，评测集要重标注 ——
那是另一个量级的实验，不适合当第一次。

**改动**：`src/lib/retrieve.ts` 的 `export const TOP_K = 3;`，只这一行。

**结果（三指标完全没动）**：

```
            @1      @3      @5        线上生效口径
K=5       0.740   0.960   1.000        1.000 (@5)
K=3       0.740   0.960   1.000        0.960 (@3) ← 少了 0.040
```

**答案层才是真相**：`--with-llm` 命中数 **25/25 → 24/25**，唯一掉的是 c23。

| | c23（问"工作三年笔记本能换新吗"，期望 chunk4 排第 4） |
|---|---|
| K=5 | 引 [4] 答"折旧周期 4 年，未满期暂不能申请更换" ✓ |
| K=3 | chunk4 掉出上下文 → **"文档中没有相关内容"** ✗ |

**回滚理由**：`TOP_K` 从 5 降到 3 对这个 9 块的库意味着覆盖率 55%→33%。
三指标不动是因为**评测深度固定 5**（V14 修的那条），恰好把"线上实际只取 3 条"
这个事实挡在了指标外面；只有"线上生效口径 @3 = 0.960"和答案层的 24/25 露出来。
→ **教训：调 RAG 参数时，只盯 recall 会漏掉一半真相。**
检索指标管"期望块在不在候选里"，答案层管"LLM 有没有拿到能用它的上下文"，
两者必须同时看（这正好是 spec C4-b 存在的理由）。

> 这次也顺带验证了 C3 的判据是可行的：改小 K 是**看着没变差、实际变差**的典型，
> 如果只按三指标下结论，会把它当成"无影响的等价改动"保留下来。

### 第 2 次：prompt v1→v2（禁止 markdown）+ 采样参数固定（保留）

这轮分**两段**做，顺序不能换（V18 ⑤）：先固定采样证明"测量稳定了"，
再改 prompt 做对比。两段混在一起就分不清"星号消失"该记谁的功劳。

#### 前置轮：`temperature` 从"未设"→ `0`（只改采样，prompt 不动）

改法：`sampling.temperature` 写进 `rag-prompt.json`，`llm.ts` 与 `eval.mjs`
都读它 —— 线上与评测必须**同源**，否则测的不是线上行为。

**稳定性验证（同配置连跑两次 `--with-llm`）**：

| 指标 | 第 1 次 | 第 2 次 |
|---|---|---|
| 关键词命中 | 25/25 | 25/25 ✓ |
| 逐条答案文本 | — | **6 条措辞不同** |

结论：**`temperature=0` 让"命中数"稳定了，但没有让答案逐字稳定。**
例：c10「上限是 380 元」/「上限为 380 元」；c17 一次多了一句"当日往返不超过 8 小时减半"；
c23 一次「未满 4 年折旧期，暂不能申请更换」、一次「文档中没有相关内容」。
→ 所以 C4-b 只能比**关键词命中数**（稳定），不能比字面或单条答案质量（不稳定）。
这不是模型"不听话"，是服务端推理本身的非确定性 —— 要求逐字一致就是 V12/V17 同类错误。

#### 对比轮：prompt v1 → v2（新增规则 4：只用纯文本，禁止 markdown）

**对照设计**（反证法）：为了确认"星号消失"是 prompt 的作用而不是温度的作用，
先把规则 4 临时摘掉、保留 `temperature=0` 跑一遍做对照：

| 组 | prompt | temperature | 答案里的 `**` | 关键词命中 |
|---|---|---|---|---|
| 对照 | v1（3 条规则） | 0 | **3 处** | 25/25 |
| 实验 | v2（4 条规则） | 0 | **0 处** | 25/25 |

→ 星号是 prompt 规则 4 消掉的，与采样参数无关。**归因成立，规则保留。**
c07 现在答「年度培训基金为 8000 元，可用于外部课程…」，页面上不会再有星号。

**顺带修掉一个隐患**：给 rules 加第 4 条后，`llm.ts` / `eval.mjs` 里硬编码的
`4. citationRule` / `5. historyRule` 会撞号（两条都是 `4.`）。已改成动态编号
（`rules.map((r, i) => (i+1) + '. ' + r)`）—— 不报错、不影响运行，
但会让模型把两条规则当成同一条，优先级失真。
**教训：任何"规则编号"都不该写死在拼接代码里，它属于数据。**

**检索指标不受影响**（prompt 只在检索之后才用上）：@1 0.740 / @3 0.960 / @5 1.000 全部不变。
`--check` 现在会打印 `prompt: rules=4 条 / temperature=0`，改 prompt 的人能立刻看见版本。
