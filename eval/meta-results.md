# W17：元数据注入 —— 四组对照结果

> 运行时间：2026-11-01
> 用例：52 条（49 单跳 / 3 多跳），知识库C（6 篇文档 / 40 块）
> 复现：`npm run eval:agent -- [--no-meta] [--hint]`

---

## 1. 结论

**给每个检索片段标上「生效日期 · 是否已废止」，让 Agent 平均少查 0.6 次、少花 28% 的 input token，
答案一条不掉。而 W16 加的那条「指路提示」在两种配置下都是净负收益，已改为默认关闭。**

| 组 | 元数据 | 指路提示 | 答案 | 检索/问 | token/问 | p95 |
|---|---|---|---|---|---|---|
| A0 | ✗ | ✗ | 52/52 | 2.04 | 6486 | 10201ms |
| **A1** | **✓** | **✗** | **52/52** | **1.44** | **4641** | **8794ms** |
| A2 | ✗ | ✓ | 52/52 \* | 2.25 | 6703 | 11627ms |
| A3 | ✓ | ✓ | 52/52 | 1.52 | 4730 | 7924ms |

\* A2 首轮跑出 51/52，唯一失败的是 c22。查证后确认是**判据太窄**（要求答案含「分级」，
模型答的是「住宿定额标准」，而 G 文档原文写的是"按城市分级定额"），修正判据后复跑两次均通过。
详见第 5 节 —— 这条如果不查，会得出"提示会让答案出错"这个**错误且更戏剧化**的结论。

> **A1 就是现在的线上配置**（元数据默认开、提示默认关）。

**复跑验证**：改完默认值后按线上配置又完整跑了一次 ——
`52/52，1.46 次/问，4593 token/问，证据覆盖 100%，p95 6518ms`。
与 A1 的 1.44 / 4641 只差 0.02 次、1%，说明这组数字可重复。
（p95 从 8794 降到 6518 是运气 —— 单次运行的 p95 受最慢那几条影响，波动本来就大，
不要拿它做跨组比较，看均值。）

---

## 2. 为什么是四次完整运行而不是一次

要证明「元数据替代了一次检索」，单独看"加了元数据之后变快了"是不够的 ——
变快也可能是因为同时改的别的东西。所以把两个因素拆成 2×2：

- **为什么必须能单独关掉指路提示**：W16 的结论是"提示救活了 m02"。如果只测"加元数据"，
  m02 变便宜了，我无法判断是元数据的功劳，还是提示本来就在起作用。
- **为什么必须能单独关掉元数据**：A2（只有提示）是 W16 那套的复现。

两个开关都是环境变量（`AGENT_DOC_META` / `AGENT_POINTER_HINT`），不是配置项 ——
它们是实验条件，不该出现在 `.env.example` 里给运维调。

---

## 3. 三个发现

### 3.1 元数据是主力：-0.60 次检索、-28% token、答案不掉

A0 → A1 只变了一个因素（加上元数据）：

```
检索 2.04 → 1.44 次/问  (-29%)
token 6486 → 4641 /问  (-28%)
p95   10201 → 8794ms   (-14%)
答案  52/52 → 52/52
```

### 3.2 指路提示是净负收益，两种情况下都是

| 对照 | 检索 | token |
|---|---|---|
| A0 → A2（无元数据，加提示） | 2.04 → **2.25** (+10%) | 6486 → 6703 (+3%) |
| A1 → A3（有元数据，加提示） | 1.44 → **1.52** (+6%) | 4641 → 4730 (+2%) |

**加了提示，模型就真的会多查。** 这句话在 W16 已经被观测到一次（当时是 1.13 → 2.63），
W17 又独立复现了一次。两次实验的元数据条件、用例集、模型版本都不同，方向却一致，
所以这不是一次采样波动的巧合。

机制上说得通：指路提示是在工具结果末尾追加一句"这个块指向别处，你可能需要再查一次"。
模型的默认行为是**服从工具输出里的建议**，于是即使它已经拿到了能回答的证据，也会照着去查。
而每一次多余的检索，都要付一次完整的前向 + 一次完整的上下文重读。

### 3.3 两者叠加不如只用元数据

A3（1.52 / 4730）比 A1（1.44 / 4641）都差一点。差异不大（0.08 次检索、2% token），
但方向是负的，而且 A2 已经单独证明了提示的负作用。

**结论：元数据做的是"把事实摆到模型面前"，指路提示做的是"催模型再动一次"。前者省的是一次检索，
后者花掉的是一次检索。** 有了前者，后者就纯粹是成本。

## 4. 谁受益最大

A0 → A1 逐条 token 降幅前六（全部答案不变）：

| 用例 | 类型 | 检索 | token | 问题 |
|---|---|---|---|---|
| c22 | 改述·费用报销 | 3→1 | 9436→3651 (**-5785**) | 出差住酒店的费用怎么报？ |
| v05 | 版本冲突·报销 | 3→1 | 9159→3699 (-5460) | 报销单据应在费用发生后多少个工作日内提交？（旧版 15 天 / 现行 30 天） |
| v02 | 版本冲突·考勤 | 3→1 | 8936→3634 (-5302) | 一个月内累计迟到几次会取消当季度绩效奖金参评资格？ |
| m02 | 多跳 | 4→2 | 9606→4580 (-5026) | 成都研发中心员工的婚假是多少天？（指针 → 母公司标准） |
| s05 | 主体区分·带训 | 3→1 | 8585→3679 (-4906) | 成都研发中心新员工的导师带训期有多长？（8 周 / 母公司 6 周） |
| s04 | 主体区分·绩效 | 3→1 | 8448→3676 (-4772) | 成都研发中心绩效 S 档最多可以占多少人？ |

**共同点：这几道题在库里都存在"看起来一样、实际上不同"的两份材料**（2024/2026 两版手册，
或母公司手册 vs 研发中心制度 vs 差旅办法）。没有元数据时，模型必须多查一次才能确认该用哪份；
有了元数据，第一次检索的结果里就写着"这份是 2024-01-01 的，已经被 2026 版取代"。

最典型的是 v03（辞职提前 30 天 vs 旧版 45 天）：A0 要 3 次检索、8746 token，
A1 只要 **1 次、3684 token**，答案都对。

## 5. 必须说清的一件事：A2 的 51/52 是判据误判

第一次跑完，A2（无元数据 / 有提示）少了一条：

```
#22 c22  ✗ 缺「分级」
我先检索一下知识库里关于出差住宿报销的规定。出差住宿费的报销规定主要依据
《星海科技差旅与费用管理办法》（文件编号 XH-FIN-2026-011，2026年2月1日生效）。
该办法明确：它与《员工手册》规定不一致时，以该办法为准 [6]。
因此，以下按现行口径说明：一、住宿定额标准…
```

答案本身**是好的**：它选了更具体的专项办法，还明确说了适用范围以谁为准。
失败只是因为判据要求出现「分级」两个字，而它写的是「定额标准」。

**G 文档原文第 38 行：「住宿费按城市分级定额」** —— 模型用自己的话复述了同一件事。

如果不去查证，这条会被写成"指路提示会让模型答错题"，那是一个更有戏剧性、但**完全错误**的结论。
这正是 W16 学到的：判据误判的方向是固定的，它只会把对的判成错的，于是你会去改系统，治的是假病。

修正：`answerMustContain: ["分级"]` → `answerAnyOf: [["分级", "定额", "档次", "级别"]]`。
复跑两次均通过，A2 记为 52/52。

## 6. 判据逐条核对

| 编号 | 判据 | 目标 | 实测 | 结果 |
|---|---|---|---|---|
| D2-1 | 答案层不退化 | ≥ 52/52 | 52/52 | ✅ |
| D2-2 | A1 组 m02 答对 | 必须 ✓ | ✓（2 次检索，答「12 天」） | ✅ |
| D2-3 | 平均检索次数 | ≤ 2.42 | **1.44**（A1）/ 1.52（A3） | ✅ |
| D2-4 | input token | **≤ 5800/问** | **4641**（A1）/ 4730（A3） | ✅ |
| D2-5 | 抽取准确率 | 6/6 | 6/6（人工逐条核对） | ✅ |
| D2-6 | 对齐不误判 | 无误标 | 仅 E 被标已废止，正确 | ✅ |

**D2-4 是 W16 没通过的那条**（当时 7535/问，超 +60% 的判据）。W17 做到 4641，
相比 W16 的 7535 降了 **38%**，相比 W16 的起点（无规则，3629）只高 28% ——
而 W16 那 3629 的代价是 m02 答错。

换句话说：**W16 花 107% 的 token 买了"不再照抄已废止文件"，W17 用 28% 就买到了同一件事。**

## 7. 已知局限

**① 只在一个库上测过。** 6 篇文档、40 块、全部是中文制度类公文，且都有明确的生效日期句子。
用户上传英文文档、扫描件 PDF、或者压根没写生效日期的内部通知时，抽取大概率返回 null，
那时元数据注入不产生任何东西（围栏头保持原样），行为退化成 A0。

**② 元数据的覆盖率没有纳入判据。** 现在只有"有没有注入"的开关，没有"注入了多少比例"的指标。
若某天库里的文档大量抽不到日期，token 会悄悄回到 6486 而不是报错。
→ 可观测性建议：`retrieve.done` 日志里加一个 `withMeta` 计数（未做，列为 W18 候选）。

**③ `supersededBy` 存的是文档标题字符串，不是外键。** 文档改名会让它悬空。
本项目没有重命名功能，先接受（schema 注释里写了这个取舍）。

**④ 抽样波动比想象的大。** 单条用例的检索次数在不同轮次之间可以差 2~3 次
（c13 在 A0 两轮是 3 次 / 2 次，在 A1 两轮是 1 次 / 4 次）。52 条的平均值把这个波动压到了
±0.1 次以内，所以组间差异（0.60 次）是可信的；但**任何单条结论都要重复验证**。
第 3.2 节里"提示让检索变多"这个方向有两次独立实验支撑，才敢写成结论。

## 8. 复现

```bash
# 默认组（A1：有元数据 / 无提示）= 线上行为
npm run eval:agent

# 无元数据 / 无提示
npm run eval:agent -- --no-meta

# 有元数据 / 有提示
npm run eval:agent -- --hint

# 无元数据 / 有提示（W16 那套）
npm run eval:agent -- --no-meta --hint
```

每次全量 52 条约 5~8 分钟（取决于检索次数），主要耗时在 DeepSeek 的生成。
