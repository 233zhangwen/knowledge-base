## 0. 一句话结论

**这周最大的产出不是"多跳能力"，是发现过去两个 W 的 Agent 评测跑的是一份手抄的、已经过时的检索副本 —— 修正后，真实成绩是 52/52，而不是 W15 报告的 44/45。**

多跳那部分也做了，但**没有通过我自己定的成本判据**（token +107% vs 上限 +60%），所以这一版属于"能跑、有数据、不该直接上线"，理由见第 6 节。

## 1. 先说那个必须纠正的结论

W15 的报告里写着：

> 答案层 42/45 → **44/45**。剩下的 c19 需要跨块推理，两档都答不出，属于能力边界。

**这句话是错的。** 用生产代码跑一次 c19：

```
问：一名正式员工在同一年里休完年假与婚假，合计最多可休多少天带薪假期？

答：知识库里有两份员工手册，两份手册对年假和婚假天数的规定不一样，因此我按各自版本分别计算：
    一、按《C-星海科技员工手册-完整版》正式员工每自然年带薪年假 17 天…婚假 12 天…
    合计 29 天；如果符合异地路程费条件，最多为 32 天。
```

**它答对了，而且自己处理了版本歧义。** c19 从来不是能力边界。

根因：`scripts/eval-agent.mjs` 里有一份 `searchChunks()`，是 `retrieve.ts` 的手抄副本，抄的是 W13 之前的版本：

| 能力 | 线上 `retrieve()` | eval-agent 的副本 |
|---|---|---|
| rerank 精排 | ✅ W15 | ❌ 没有 |
| RECALL_K 粗排 | ✅ 10 | ❌ K=5 直出 |
| 围栏 `<<<DOC>>>` | ✅ W14 | ❌ 裸拼 `[n]` |
| suspicious 标记 | ✅ W14 | ❌ 没有 |

也就是说 W14 的注入防御、W15 的 rerank，**Agent 路径一次都没被测过**，而这个副本已经跑了两个 W。

### 修法：不抄了，直接 import

```ts
const { runAgentTurn } = await import('../src/lib/agent-llm.ts');   // 真循环、真 prompt、真编号
const { retrieve, TOP_K, RECALL_K } = await import('../src/lib/retrieve.ts');
```

代价是要过两道 Node 的坎，都在 `scripts/lib/` 里解决了：

| 坎 | 现象 | 解法 |
|---|---|---|
| tsconfig paths | `@/generated/prisma/client` Node 不认 | 该处改相对路径（`prisma.ts` 有注释说明为何不能改回去） |
| 无后缀导入 | `from './embedding'` Node 要求带 `.ts` | `ts-resolve.mjs` 解析钩子，失败时按 `.ts/.tsx/index.ts` 重试 |
| JSON 导入 | 需要 `with { type: 'json' }` | `register.mjs` 的 load 钩子把 `export default <json>` 转成模块 |

**这三个钩子替代的是"生成一份补了后缀的副本"的老办法（W15 用过）。副本就是漂移的来源，这次把病根拔了。**

## 2. 判据本身也是被测对象

修完漂移，45 条基线跑出来 43/45。逐条看，两条都是**判据误判**：

| 用例 | 判据要求 | 模型实际回答 | 真相 |
|---|---|---|---|
| c12 | 包含「禁止」 | 「**不可以**。办公电脑上**不能**自行安装…」 | 语义完全正确，只是没用那两个字 |
| s05 | 包含「8 周」 | 「导师带训期为**8周**（母公司为6周）」 | 差一个空格 |

这类误判的方向是固定的：**只会把对的判成错的**。于是你会看到"成绩不好"，去改 prompt、改检索、加 rerank —— 治的全是假病。

顺带查出 c12 的 `expectChunks` 指向 C#4（「上限为 380 元」，餐费条款），而问题问的是装软件。**标注自洽但语义指错**（snippet 确实匹配块首，check 因此放行）。

处理：
- 新增 `scripts/lib/answer-match.mjs`，两个评测脚本共用：归一化（去空白含全角、全角数字转半角）+ 显式 `answerAnyOf`（同义词组，由人判断，不做智能匹配）
- c12 标注修正到 C#5，判据改为 `answerAnyOf: [["禁止","不可以","不能","不得","不允许"]]`

> **策略是"宁可严格"**：误判为错→有人发现并修正；误判为对→静默掩盖。所以归一化只做无损的，同义词必须显式声明。

修完后：**45/45**。

## 3. 多跳题：造 7 条，只有 3 条合格

### 3.1 为什么要先验证

"看起来像多跳"和"真的需要多跳"是两件事。如果一条题一次检索就能拿全证据，那它测的是模型会不会算，不是会不会跳。

所以新增 `--probe`：**只用原问题检索一次，看 evidence 覆盖率**，覆盖率 < 100% 才算合格。

### 3.2 结果（7 造 3 留）

| id | 类型 | 设计意图 | probe 判定 |
|---|---|---|---|
| m01 | 桥接 | 转正年假折算（问句不提"试用期"） | ✗ **一次就够** |
| m02 | 组合 | 研发中心婚假 → 母公司标准 | ✓ 缺 C#2 |
| m03 | 组合 | 研发中心绩效 S 档 → 母公司口径 | ✓ 缺 C#5 |
| m04 | 桥接 | 2024 版年假 → 现行版废止声明 | ✗ **一次就够** |
| m05 | 术语桥接 | 外包人员 × 秘密级定义 | ✗ **一次就够**（见下） |
| m06 | 组合 | 出差伙食补助 × 两套标准 | ✗ **一次就够** |
| m07 | 组合 | 实习生年假（3 条证据） | ✓ 缺 C#2 |

**被否决的 4 条不是白做**，它们降级成单跳回归题留在集里 —— 内容本身有价值，只是不够格当多跳题。这个"降级"动作要写出来，否则下一个人会以为它们本来就是单跳题。

### 3.3 为什么这个库造不出更多多跳题

40 块、`TOP_K=5` 覆盖 12.5%，而**人事类证据块一共就那么五六个**。只要问题落在同一个领域内，rerank 一次就能把相关系数最高的 5 块全端上来。

m02/m03 之所以合格，不是因为它们跨文档，而是因为问句里有个**强主体锚点**（"成都研发中心"），把 top5 锁死在 F 文档，C 的块被挤出去了。

所以在本库上，合格的多跳题必须满足：**问句带强锚点 + 第二跳证据在另一个主体/领域**。这类交叉点本来就少。

> m05 是这次最可惜的一条：问「外包人员可以接触客户的合同条款吗」，设计上要求模型把 I#3 的"不得接触秘密级"和 H#0 的"秘密=客户名单、合同条款"连起来。但第一版我把证据标到了 H#1（那是"机密"级的重复），probe 因此误判为合格。修正到 H#0 后，一次检索就把两块都拿到了 —— **标注错了会制造假的多跳题**。

### 3.4 probe 的一个已知局限

probe 用**原问题**检索，但模型实际会**改写**问题再查（m07 就是拆成两个子问题后一次命中 3 块）。所以 probe 的判定偏保守：它说的"一次就够"是"用原句一次就够"，不等于"模型一次就能完成"。

## 4. 规划：四版演进，每次都靠数据推翻

### 4.1 起点

`agent-prompt.json` 里原本没有任何"要多跳"的指示。实测平均检索 **1.13 次/问**，绝大多数题查一次就收工。

### 4.2 四版对照

| 版本 | 做法 | 检索/问 | token/问 | p95 | m02 |
|---|---|---|---|---|---|
| 起点 | 无规则（45 条） | 1.13 | 3629 | 5375ms | — |
| v1 | prompt 加「指路要追」+「版本要核」 | 2.62 | 8234 | 10825ms | ✓ |
| v2 | 收紧 v1 的版本规则（"已出现冲突"才核） | 2.71 | 8485 | 11334ms | ✓ |
| **v3** | 指路规则**下沉到代码** + 检索预算 3 次 | **2.42** | **7535** | 11797ms | ✓ |

### 4.3 两个关键教训

**① 条件句式的规则，模型判不准。**

v1 的做法是加一句"若出现『按《X》执行』就再查一次"。结果是 **49 条单跳题平均检索从 1.13 涨到 2.63** —— 它们本来一次就够。原因不是模型笨，是它无法可靠判断"我这次看到的算不算指路句"，于是**一律多查一次保平安**。

v3 把判断交给正则（`pointerHints`），模型只负责执行"看到提示就查"。判断该待在出题人写死的地方。

**② 但确定性检测也会误报，因为正则不看相关性。**

第一版 `pointerHints` 扫全部 5 块，结果**每条题都触发**：问"年假多少天"，top5 里混进研发中心的婚假条款（「按母公司标准执行」），于是每条题都被提示去查母公司手册。

收窄到**只看 top-1**：排第一的块如果指向别处，说明答案确实在别处；排第五的块顺带提到另一份文件，多半只是同章节的邻居。

### 4.4 m02 的意义

> 无规则时：「按成都研发中心制度…适用母公司《员工手册》的标准：婚假为 **10 天**」
> —— 那是 **2024 版**的数字，现行版是 12 天。系统忠实地照抄了一份已废止的文件，**而且它自己不知道**。

有提示后：

> 「目前现行有效的母公司《员工手册》，是 2026 年 1 月 1 日起施行的完整版；**它同时废止了 2024 版** [9]。按照该版手册规定：婚假为 12 天…」

这不是"指标涨了"，是**一次事实性错误被拦住**。和 W15 的 c14 是同一种病。

## 5. 压缩：去重是免费的，而且量化得出来

### 5.1 之前就在浪费

```ts
// 改之前：编号复用，正文照旧完整注入
let no = ledger.numbers.get(c.id);
if (no === undefined) { 分配新编号; push citations }
return fenceChunk({ no, ..., content: c.content });   // ← 同一段 500 字进来第二遍
```

### 5.2 改之后

二次命中的块只回一行占位：

```
[3] （《C-星海科技员工手册》第 3 段：内容与前文已给过的同编号片段完全相同，此处不再重复）
```

编号仍复用，引用不乱；正文不重复。**无损** —— 没删任何信息，只是不再重复同一份。

### 5.3 用确定性指标衡量，而不是 token

第一次想用 token 验证，结果是"去重后 token 反而涨了"（11062 vs 10735）。原因是那次 m02 检索了 5 次而非 4 次 —— **模型的多跳次数本身在波动，token 总量被次数淹没**。

改成记录 `agent.chunks { total, fresh, repeated }`，这是与调用次数无关的比率：

| 阶段 | 检索次数 | 块数 | 重复块 | 重复率 |
|---|---|---|---|---|
| 去重前 | 141 | 705 | 183 | 26.0% |
| 去重后 + 预算 | 115 | 575 | 118 | **20.5%** |

**多跳场景下，每 4~5 块注入里就有 1 块是重复的。** 这个数字不依赖采样，可复现。

### 5.4 检索预算：3 次

`AGENT_MAX_STEPS=6` 管不住过度检索（它同时要留给生成步骤）。加了 `AGENT_MAX_RETRIEVALS=3`：第 4 次起返回一句提示让模型基于已有资料作答，**不抛错**（抛错会被 SDK 当成"工具故障"回传给模型，模型可能去解释"检索服务异常"，误导用户）。

实测拦住 11 次。

3 次的依据：多跳题的实际需要是「首查 → 追指针 → 核版本」，正好 3 步；单跳题 1~2 步。

### 5.5 没做的那一档

spec 的 C1-b（超限裁剪）没做：流式已经发出去的内容撤不回来，能做的只有"不再注入新块"，那会丢证据。用预算从入口控制，比在出口删更干净。

## 6. 未达标声明

| 判据（spec D2） | 目标 | 实测 | 判定 |
|---|---|---|---|
| 多跳题通过 | ≥ 6/8 | 3/3（题只有 3 条） | 样本不足，不算通过 |
| 单跳题不退 | 不低于基线 | 49/49（基线 45/45） | ✅ |
| input token 增幅 | ≤ 60% | **+107%** | ❌ |
| p95 延迟 | ≤ 12s | 11797ms | ⚠️ 压线 |

**不达标就是没达标，不调判据。**

但这组数字要连着看：+107% 的 token 换来的不只是 m02 一条题，而是"不再照抄已废止文件"这个行为改变。它是产品决策，不是技术指标 —— 所以正确的处理是**把选择权交出去，而不是替用户决定**：

- 想省钱：把 `AGENT_MAX_RETRIEVALS` 调到 1，行为退回接近起点（m02 会重新答错）
- 想要正确：保留 3，接受 token 翻倍
- 想两者都要：见第 7 节的元数据方案

## 7. 已知风险与下一步

| 风险 | 说明 |
|---|---|
| **库规模** | 3 条多跳题是在 40 块库上筛出来的。库涨到几百块，锚点效应减弱，需要重造 |
| **指路正则** | 只覆盖「按《X》」「按母公司标准」等几种写法。真实文档里"依照""按照""详见"变体很多，漏检即少查一次 |
| **top-1 启发式** | "第一块指向别处"不等于"答案一定在别处"。如果 rerank 把指路块排到第一而答案就在同块，会多一次无用检索 |
| **预算 3 次** | 需要 4 跳的题会被截断。目前没有这种题，但库长大后会有 |
| **单次运行** | 所有数字都是单次跑。模型多跳次数在 2~5 之间波动，结论对单条题不稳，只有聚合指标可信 |

**下一步（W17 候选）：把"生效日期"做成元数据注入。**

m02 的根因不是模型不会核对，是它**拿到的块里没有版本信息**（E#2 只在标题里写了"2024 版"，正文没有生效日期）。每个块注入时带一行 `生效日期：2026-01-01`，模型第一次检索就能判断该用哪版，**省掉整整一次检索（约 1800 token）**。

这也正好接上 W15 的结论：rerank 治不了符号消歧，那是元数据问题。
